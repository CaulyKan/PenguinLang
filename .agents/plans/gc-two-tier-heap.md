## 0. 本计划要解决什么

§10.2 的"两个堆"要落地，但 §10.4 给的提升手段对**一般引用类型不可行**：

> §10.4 原话：**已经被多处引用的不可变对象**（比如同一个字符串既在本地容器里、又要写进通道）：
> **按值语义复制一份进共享区，不保持身份**。

"按值复制"只对扁平结构（字符串）成立。一般引用类型做深拷贝要同时处理**别名**（复制后身份分裂）、
**循环**、以及"复制出来的图是否还可能指回本地堆"。而且它要求程序**不依赖跨线程对象身份**
（§10.4 自己也承认要单独做一次审计）。

**替代方案（本计划的主题）**：对象**留在原 span 不搬家**，只在移交点给它（及其必保的闭包）
**置一个 `shared` 位**：

- 本地回收器：带 `shared` 位的槽**永不回收、不当根、不穿透**（保护位）；
- 全局回收器：**保持今天的全量标记清扫语义**（全套根、穿透一切对象），负责带位对象的释放；
- 不需要深拷贝、不需要搬运机械、也不需要"全局标记只走共享侧"。

**收益模型（方案 F，评审定稿）**：双层堆的收益**不**来自"全局标记 = O(共享存活集)"，而来自两件事：

1. **本地回收消化本地 churn**：churn/live ≈ 11× 里的大头是本地短命对象；本地配额高频回收它们，
   全局 goal 只由共享侧分配推动 ⇒ **全局收集频率大幅下降**（对照基线 19 次 / GC 5.73 s）；
2. **本地回收只停本域**：其他 worker 照常跑。

**明确放弃的**：全局收集的**单次暂停不随共享存活集缩小**（≈今天的 ~300 ms/次不变）。
这是方案 F 的取舍，换来两样东西：

- **全局收集器几乎一行标记逻辑都不用改**（今天的行为就是目标行为，只改触发预算）；
- **语言表达力无损**：更激进的"闭合性"方案（禁止"本地对象引用带位对象"，让全局标记只走
  共享侧）会把"接收方把消息存进本地容器"（缓存 / 批处理 / 关联 / 窗口——通道消费者的日常）
  变成非法，且无法事后改造（级联提升要枚举引用者闭包 = 别名集合运行时不可枚举，与"动态冻结"
  被否决同源）。全量全局标记下，反向边从 帧 → 本地对象 → 带位消息 一路穿透，存活无死角。

一句话：**"两个堆"是逻辑分区（逐对象保护位 + 预算归属位），不是标记边界。**

## 2. 设计

### 2.1 三个策略（按对象形状分流）

| 对象形状                                    | 手段                                                                                                | 理由                                       |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| 值类 / `ICopy` / 扁平不可变（`string`）     | **按值复制**（§10.4 原方案）                                                                        | O(1)、复制隔离发送方后续修改、最干净       |
| **`Imm` 的引用图**（深不可变、`!mut` 冻结） | **原地置 `shared` 位**（本计划）                                                                    | 绕开深拷贝 —— 它真正的用武之地             |
| 可变对象                                    | **不得"就地"移交**：分析能预测时在临界区内新造（分配即置位）；或走 `Ownership` move；否则检查器拒绝 | 本地仍有别名时置位 = 数据竞争（Inv-S3/M7） |

**为什么 `Imm` 是硬前提**（两条，缺一不可）：

1. **数据竞争**：把可变对象标成共享，别的线程就能通过共享对象读写它，而本地线程仍无锁地改同一个对象；
2. **撕裂读 → 漏标 → 误释放**：本地回收器要读 `shared` 对象的字段来标记。对象可变而别的线程在写时，
   读到的是半新半旧的指针，漏掉一个引用就会在下一轮把活对象当垃圾。

这也是文档已经否决"动态冻结"的同一条理由：

> "没人持有"不可靠：**可变性是逐绑定的权限而不是对象状态，别名集合运行时不可枚举**

所以判据必须是**静态的 `Imm(T)`**（已可判，见 §1），不能靠运行时观察。

### 2.2 存储布局（字节账已核实）

**GtSpan：128 B 已经用满，没有余量。** 需要为"本 span 里有没有 shared 对象"提供一个 O(1) 判据：

```
现状（恰好 128）:
  magic u32(4) | size_class u8(1) | flags u8(1) | nslots u16(2) | free_index u16(2)
  | live_count u16(2) | rep_slot u16(2)          = 14 → pad 16
  | alloc_bits u64[4](32) | gray_bits u64[4](32) | black_bits u64[4](32)
  | next ptr(8) | super ptr(8)                   = 128 ✓
```

**方案（评审后收紧）**：`nslots` 降为 **u8**（最大 252 < 256）腾出 1 字节，放 **`uint8_t nshared`**：

```
新布局（15 字节 → pad 16，仍有 1 字节余量）:
  magic u32(4) | size_class u8(1) | flags u8(1) | nslots u8(1) | nshared u8(1)
  | free_index u16(2) | live_count u16(2) | rep_slot u16(2)     = 15 → pad 16
```

**不要把 `flags` 位域化**：`GT_F_*` 三位之外要留余量给未来 span 级标志（例如物理分区的 `GT_F_SHARED`）。
⇒ **`GT_SPAN_HDR` 保持 128，size class 表（`gt_classes[]` 的 nslots）完全不动。**

**GCHeader：用现有 padding，绝不加长。** 现状 `{next(8), marked(4), is_string(4), size(4)}` = 20 → 补齐 24。

```
加 shared：放进那 4 字节 padding（或与 is_string 合成一个 flags int）→ sizeof 仍为 24 ✓
```

> **必须保持 24 B**：`_emperor_gc_alloc_charge()` 与 gc_torture 的"精确存亡差值"断言都按 24 B 头算账，
> 头一变大那些断言与 heap 记账全部要重算。

`shared` 位读写的成本边界：
- **原地置位只在移交点/写点发生**（本域线程，O(1)）；
- `nshared == 0` 的 span（绝大多数）走**今天完全相同的快路径**：本地清扫纯位图运算、
  整块回收（wholesale recycling）照旧；
- 只有 `nshared > 0` 的 span 需要逐槽读 `GCHeader.shared`（少数 span，可接受）。

### 2.3 移交点（§10.3 五条）的置位动作

| 移交点                                      | 动作                                                 |
| ------------------------------------------- | ---------------------------------------------------- |
| 可偷创建点的上下文字段填充                  | 值/`Imm` → 复制；可变 → 检查器拒绝或直接分配在共享堆 |
| 同步通道的写入                              | 同上；`Imm` 图 → 置根 `shared` 位                    |
| `Ownership` 的移交                          | 全图新鲜 → **真移动**（零拷贝）；否则退回复制/拒绝   |
| 全局变量初始化 / 写入全局同步对象           | 同"通道写入"                                         |
| 可偷创建点结果容器 `complete()`（**易漏**） | 同"通道写入"，且注意它是**跨线程**的（见 §2.4）      |

### 2.4 唯一的洞：闭包跨域（**待决策 D1**）

需要的不变量不是一个"根被标记"，而是：

> **Inv-S1**：**带位对象的整个可达闭包都带位。**

否则：本地回收器遍历到"住在别的域 span 里的闭包成员"时（正确地）不穿透带位对象，
而那个成员未带位 ⇒ 本地视角它是死的 ⇒ 误回收 —— 而共享对象还指着它 → use-after-free。

三种保证方式（三选一，M0 结束时必须定）：

- **(a) 移交点检查域归属**：遍历闭包（闭包冻结 ⇒ 遍历无竞争），只对"非本域"的成员补位。
  代价：移交点可能持锁（通道写入在锁内）走图 → 需要工作列表 + 上限。
- **(b) 检查器静态保证**（**推荐**）：只允许"**闭包必然在本域构造**"的 `Imm` 图走原地置位
  （可静态判定的子集；`Ownership` 的全图新鲜性检查就是现成先例），其余退回复制/共享堆。
  代价：无运行时遍历；收益取决于分析精度（不精确只是少走这条路，不损失正确性）。
- **(c) `GC_VERIFY` 兜底断言**：无论选哪种，(c) 都必须做 —— debug 构建里当场报错。

### 2.5 本地回收器

- **触发与预算拆分（收益的兑现机制）**：域本地分配配额（形态照抄现有的 young 预算，但**按域**计）；
  **本地分配不推全局 goal**——全局 goal 只由共享侧分配/存活推动，这是"全局收集频率下降"的实现方式。
  带位槽的字节**从本地配额里剔除、计入共享预算**（sweep 时用 `nshared` × slot 统计）——否则本地堆被
  "本地收不动"的带位对象占满，本地回收空转抖动。本地回收后 live 的下降要折进全局 unified goal
  的重算（否则 goal 虚高、堆峰值上涨）。
- **根集合（完备性是正确性问题，评审洞 1）**：本域协程帧链（含停驻栈）+ 本域 arena 隔离环 +
  **全局根与保守 region 注册表的本域过滤**（只取指向本域 span 未带位对象的槽）。为什么必须有
  后一项：封闭类全局变量（4.3 第三类）与 scheduler 的容器缓冲引用的对象可能是本域未带位对象——
  本地根看不到它们 ⇒ 误收 ⇒ 全局变量/容器悬垂。全局根是千级槽位，每次本地回收过滤一遍是微秒级。
  （typed region 已随 native-arrays 删除；保守 region 注册表保留。）
- **标记**：span 集合限定为本域；**带位对象不当根、不穿透**（Inv-S8：它们可能正被其他域持锁写，
  穿透 = 撕裂读 = 漏标 = 误释放）；**大对象不释放、但要穿透**（评审洞 2）：从本地根可达的大对象要读
  它的 refmap 继续标记它指向的本域 span 对象——否则"帧 → 大对象 → 本地对象"的中转链在叶子上断掉，
  本地对象被误收。安全性：未带位大对象只被本域引用（Inv-S5）⇒ 本域停了就无并发写。
  大对象**本体**的释放仍归全局（malloc 索引不在本地）。
- **清扫**：`alloc & ~black & ~shared`；`nshared == 0` 的 span 保留整块回收；带位槽一律跳过。
  **清扫零用户代码**（finalizer 已随 native-arrays 删除）——纯位图运算，无重入、无分配、无时序问题。
- **执行者与暂停范围**：本地回收由**本域 worker 在安全点就地执行**（无专用 GC 线程，ORCA 同款
  —— GC 融入执行流而非独立线程）；**只停本域协程**，其他 worker 继续跑 —— 这是本计划最重要的收益。
- **本地回收必须可靠地定期跑**：全局全量清扫虽然会顺带收本地死对象（§2.6），但全局触发只看共享侧
  ——本地堆的健康完全依赖本地配额触发（见 §5 性能验收）。

### 2.6 全局回收器：保持今天的全量语义（方案 F 的核心）

- **标记**：**不改**——从**全套全局根**（主栈 + 全部协程栈扫描区 + 全局根 + 同步对象内部引用 +
  新对象隔离环 + 保守 region 注册表，即 §10.8 原文全套减 meta pin）出发，**穿透一切对象**
  （带位、未带位、大对象），全量判定生死。反向边（未带位 → 带位）因此**天然安全**：接收方把消息
  存进本地容器后，全局标记从 帧 → 本地对象 → 带位消息 一路穿透，存活无死角——**不需要任何
  "发现机制"**（注册表 / 上报 / epoch / 自扫，全都不要，见 §2.10）。
  （注：§10.8 原文的"元编程钉住的对象"一项**已随 unsafe_cast 删除轮失效**——pin 表已删，meta 对象
  现在是 `MetaEngine.object_values` 里的**常规引用**（List/array refmap 精确追踪、全局根可达），
  不再是特殊根；B6 应用时把设计文档 §10.8 同步修正。）
- **清扫**：**不改**——全量清扫，顺带释放本地死对象（全量标记已经看到死活，顺手清扫零额外成本；
  这也是本地回收的兜底）。
- **唯一改动**：**触发预算拆分**——本地分配走本地配额（不推全局 goal），全局 goal 只由共享侧
  分配/存活推动。这是"全局收集频率下降"的兑现机制，其余一切都是今天的行为。
- **纪律**：全局收集把各域隔离环/保守 region **当根扫描但不清空**（清空会丢在途临时值的根）；
  全局收集与本地收集互斥（§2.13）；全局清扫后位图清干净（今天的行为），本地回收结束前同样要清
  （M4 的位图纪律）。

### 2.7 不变量集（在 §10.6 现有四条之上新增）

### 2.9 共享容器的写入口：**写点提升**（Inv-M1..M7）

**先记下被否掉的方案：出口全图穿透扫描。** 早期的"`with()` 出口遍历载荷整图、遇已带位不停"
既做不到也不安全（评审 P1）：

1. **与"已标记即停"互斥**：要发现挂在已带位 `p.child` 下面的 `newY`，就必须**穿透** `p.child`
   继续走 —— 那么"空手而归的 `with()` 只付 O(直接字段数)"不成立，成本是 **O(整个载荷图)**。
2. **穿透会读到别人临界区里的撕裂值（硬伤）**：一张对象图**可以同时挂进两个容器**（把已带位对象
   再放进另一把锁是合法的，它已经在共享侧）。于是 A 持**自己的**锁做出口扫描、穿透读 `X` 的字段时，
   B 可能正持**另一把锁**写 `X` ⇒ 读到半新半旧的指针 ⇒ 漏标 ⇒ 孙对象未置位 ⇒ 被本域回收 ⇒ 释放后还在用。
   Inv-M2 的"锁内完成"只保护**本锁的载荷**，保护不了图里属于别人临界区的部分。

**正解：提升发生在"写点"，从「新值」出发，遇已带位即停。**

```
promote_from(new_value):
    从 new_value 出发（它刚被造出来、别人还看不见 ⇒ 读它的字段无并发）
    给每个经过的对象置 shared 位
    对每个引用字段：未带位 → 继续走（worklist 迭代，不递归）
                    已带位 → 停
```

**为什么这里的"遇已带位即停"是安全的**（与出口扫描的本质区别）：遍历方向是**从新值指向旧值**。
新值只有本人持有 ⇒ 读它无并发；遇到的旧值若已带位，由 Inv-S1（带位对象的闭包全带位）它自己的子图
已经完备，**不需要读它的字段** ⇒ 无撕裂读。出口扫描的方向正好相反（从载荷指向子对象），
必然要读**可能正被别人改**的已带位对象 ⇒ 不安全。

**写入口的取值约束（Inv-M7）**——写进共享对象的新值分两类：

| 合法来源                                       | 提升动作                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **已带位对象**（已在共享侧）                   | 无需动作                                                                                    |
| **本临界区内新分配的图**（`new` 表达式的结果） | 从新值出发提升 —— 也可更省：**临界区内分配即置位**（见下）                                  |
| **`Ownership` 的 `.move()` 结果**              | 移交时显式提升整图（图新鲜 ⇒ 只走一遍）                                                     |
| **Imm 的新值**（含被本地别名持有的）           | 从新值出发提升（Imm 不可变 ⇒ 本地别名 + 共享读**无数据竞争**，合法）                        |
| 其它（**可变**且已被本地别名/外来引用持有）    | **检查器拒绝**（Inv-M7）。本地线程仍无锁持有它 ⇒ 数据竞争 + 本地回收不穿透它 ⇒ 子图漏标误收 |

**为什么可变新值的入边也要查（评审 N1）**：`L.f = v; s.buffer = v`（v 是临界区内新分配的**可变**对象）
——只查出边会放行，提升后 v 带位、L（未带位）仍无锁引用它：数据竞争 + 本地回收不穿透 v ⇒
v 的子图对本地不可见。静态规则：**可变新值从分配点到写点不得流入任何本地堆字段**
（Ownership 全图新鲜性的**双向**版：出边查"新图引用了谁"，入边查"谁捕获了新值"）。

**两种实现形态**（建议先做 (a)，零编译器配合）：

- **(a) 分配点提升（推荐起步）**：临界区内新分配的对象即时纳入提升。**落地方式二选一**
  （"记 arena 分配序号"不可行——序号只能判断"在不在区间"，**枚举**区间成员仍只能靠隔离环，
  而它只有 512 槽会绕回）：
  ① 进临界区时把新对象挂一条"临界区专用链表"（分配器顺手 push）；
  ② **临界区内分配时立即置位**（TLS arena 里放一个"在锁内"深度计数，分配器看到非 0 就顺手置位）。
  **分配快路径的成本红线（Lattice 的教训——它把 phase guard 明确排除在分配快路径之外）**：
  `gt_alloc_small` 本来就要经 TLS 取 arena 并做 quarantine push，所以 ①② 的真实增量只是
  **已取出的 arena 结构上 +1 字段读 + 可预测分支**——相对成本可忽略；红线是**不得再往分配路径
  加更重的东西**（新的 TLS 查找、复杂 guard、锁）。
  ⚠️ **已知代价（过度置位）**：临界区内**没进载荷**的临时对象（`let tmp = new Key()`）也会被置位，
  成为共享垃圾、只能等全局收。精化选项（可后补）：出口只提升"**载荷直接字段指向的**区间内新值"
  再从它们递归——空手 `with()` 回到 O(直接字段数)，精度恢复。
- **(b) 编译器插桩（终态）**：只对"写入目标在共享侧"的字段写插桩（`with` 回调形参链、通道 `pop`
  回来的引用）——这正是 Lattice phase guard 的同款位置（**守在写操作上，不碰分配路径**），
  也是 Inv-M7 静态检查的运行时对应物：P5 落地后**只插静态证明不了的写**，可证明的零成本。
  演进线：(a) 起步（工程零依赖）→ P5 检查器 → (b) 收尾（把 (a) 的过度置位消掉）。

**统一覆盖所有共享容器**：`Mutex` 的 `with`/`set`、通道的 `push`、`Ownership` 移交、结果容器 `complete()`。
构造时的初始载荷 = **第一次写**，走同一条路径。

**约束的传递性**：`new Holder(localThing)` 这种"新对象引用了已本地别名的**可变**对象"**也要拒绝** ——
提升会把 `localThing` 一起置位，而本地还别名它 ⇒ Inv-M7 的检查必须是**全图**的（与 `Ownership`
的全图新鲜性同款）。

| 编号       | 内容                                                                                                                                                                                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Inv-M1** | 写入口必须从**新值**出发做提升（`new` 图 ⇒ 递归；遇已带位即停）                                                                                                                                                                                          |
| **Inv-M2** | 提升在**锁内**完成（**不是**"出口全图扫描"：出口扫描必须穿透已带位对象，既贵又撞撕裂读）                                                                                                                                                                 |
| **Inv-M3** | 提升覆盖新值的**整个闭包**（`new Holder(localThing)` 要连 `localThing` 一起判）                                                                                                                                                                          |
| **Inv-M4** | 提升只触及**本域 span** 的对象（跨域引用必经移交点、已带位）⇒ 无跨域位写入竞态                                                                                                                                                                           |
| **Inv-M5** | 访问权不得逃出临界区（**GC 正确性前提**：写入口约束假定"写入都在锁内"）                                                                                                                                                                                  |
| **Inv-M6** | 构造时的初始载荷走同一条路径（构造 = 第一次写）                                                                                                                                                                                                          |
| **Inv-M7** | 写进共享对象的**可变**新值必须是"已带位 / 本临界区内新分配的图 / `Ownership` move 结果"三者之一，**且全图双向无本地别名**（出边：`new Holder(localThing)` 连坐；入边：先 `L.f = v` 再 `s.buffer = v` 拒绝）。**Imm 新值不受此限**（不可变 ⇒ 无数据竞争） |

### 2.10 共享对象的可达性：全局保持全量标记，问题不存在（方案 F 定稿）

**方案 F**：全局回收器保持今天的全量标记（§2.6），因此：

- **反向边合法**："接收方把消息存进本地容器"（未带位 → 带位）是通道消费者的日常
  （本地缓存 / 批处理 / 关联 / 窗口）。全量标记从 帧 → 本地对象 → 带位消息 一路穿透，
  带位对象的存活无死角——**不需要任何发现机制**（注册表 / 上报 / epoch / 自扫，全都不要）。
- **被否决的替代路线**（留档，防止反复）：
  - ❌ **闭合性（Inv-S7 双向闭合）**：把反向边变非法 ⇒ 上述日常写法全部撞墙，且无法事后改造
    （级联提升要枚举引用者闭包 = 别名集合运行时不可枚举，与"动态冻结"被否决同源）；它换来的
    "全局标记 = O(共享存活集)"买不起表达力的损失，且单次全局暂停的缩小对本设计并非必需。
  - ❌ **同步对象注册表**：救不了非 Sync 的共享对象；"置位即注册、永不注销" = 全量泄漏。
  - ❌ **本地上报 + epoch**：存在"置位 → 首次上报"的陈旧窗口（全局收集用旧上报集 ⇒ 误收）。
  - ❌ **STW 自扫 `nshared > 0` 的 span 把带位对象当标记起点**：候选集全被标到 ⇒ 永不死 ⇒
    留在本地 span 的带位对象被永久钉住 ⇒ 灾难性泄漏。
- **`shared` 位的最终角色**：本地回收的保护位（Inv-S1/S8）+ 预算归属位（带位字节计入共享预算，
  §2.5）——不是全局标记的边界。

**两条硬规定（评审 P3 的遗产，仍然有效）**：

1. `§10.8` 的全局根集合**必须保留全套**：主栈 + **全部协程的栈扫描区** + 全局根 + 同步对象内部引用 +
   **新对象隔离环**（+ 保守 region 注册表；meta pin 一项已随 unsafe_cast 删除轮失效，见 §2.6 注）。
   隔离环是每域 arena 里的数组、不在主栈上，
   主栈的保守扫描救不了它——"唯一引用在协程帧/隔离环里的大对象"靠它们保活。
2. （方案 F 下）全局标记穿透一切对象——"不标不透"只发生在**本地回收器**对带位对象的处理上（Inv-S8）。

### 2.11 共享垃圾的归属（换出方向）

**换出的旧载荷带 `shared` 位（单调、不降级，D6）⇒ 本地回收器永不回收它 ⇒ 只有全局收集能收。**

于是这个很常见的模式会让双层堆打折：

```penguin
m.with(fun(mut s: State) -> void { s.buffer = new BigArray(...); });   // 换缓冲
```

旧缓冲的 churn 全部堆在共享堆里 → **全局收集频率回升**。而且**不能靠降级解决**：
要清 `shared` 位就得证明"没有别的线程还持有它" —— 这正是文档否决"动态冻结"的同一条理由
（**可变性是逐绑定的权限而不是对象状态，别名集合运行时不可枚举**）。

**处置 = 承认 + 引导**：

- 承认：`Mutex` 载荷的换出属于共享垃圾；**载荷峰值必须算进共享堆预算**（全局标记约 1 ms/MB 存活集）。
- 引导：**能"搬走"就别"共享"** —— 大对象/缓冲用 `Ownership` 搬运（搬出去之后本地那一侧
  就能被本地回收器回收）。
  ⚠️ **不要高估这条逃生的价值**：§9.5 明确**跨域 `Ownership` 是"接收方复制"**，所以"搬走"的成本
  也是**一次拷贝**（只是把成本从"共享堆预算"挪到"拷贝"上）。规范的判据不能只看"会不会被别的线程读到"，
  **还要带上"图多大 / 访问多频繁"两个维度**：跨域搬大图 = 一次拷贝；锁内换大图 = 一份共享垃圾；
  两者都比"小图高频"贵得多。
- 规范判据一句话：**"这个对象会被另一个线程读到吗？会 → `Mutex`/通道；不会 → `Ownership` 搬走"**，
  外加"图大不大、访问频不频繁"这一层。

（finalizer 相关的"共享对象无老家"规则已随 IMemoryDispose 删除而取消——清扫零用户代码。）

**为什么共享侧不能学 Erlang 的 off-heap binary / Lattice 的 region 整体释放（留档）**：
Erlang 的 >64KB binary 是**扁平字节**——无内部指针、无环，引用计数即可立即回收；Lattice 的
crystal region 对应"一次 freeze 的一张图"、天然整批同死。我们的共享侧是**任意对象图**——
带位对象生命周期交错、可能有环，refcount 处理不了环、region 整体释放处理不了交错——
只能全量标记逐对象回收。这是"共享 churn 只能等全局收集"的**结构性原因**，也是引导
`Ownership` 搬运（搬走的是一张整图，本地侧立即可收）的根本理由。

### 2.12 `Mutex<T>` 的访问面（与 Inv-M5 配套）

`Mutex<T>` 对**任意 `T`** 都是 `Sync` —— 约束不在 `T` 的类型上，而在**载荷怎么进来**与
**访问权怎么出去**两个时刻（构造/写入 = 移交点，§10.3 第 2 条）。

**进来的规则**：等价于一次 `Ownership` 移交 —— 复用现成的**全图新鲜性（无别名）检查**：

| 载荷形状                       | 动作                                                         |
| ------------------------------ | ------------------------------------------------------------ |
| 唯一引用的新对象               | **直接在共享区分配**（临时形态：本域分配 + 立即置位，§2.14） |
| 值类 / `ICopy` / `Imm`         | 复制进共享区，不保持身份                                     |
| `Imm` 引用图                   | 原地置 `shared` 位（§2.9 的机制）                            |
| **已被本地别名持有的可变对象** | **拒绝**（本地别名会绕过锁改它）                             |

**出去的规则**：分四档，并**放弃"给引用"那一档**（语言没有生命周期去约束它）：

| 载荷                    | 出去形态                         | 逃逸风险                         | v1 机制                                         |
| ----------------------- | -------------------------------- | -------------------------------- | ----------------------------------------------- |
| 基本类型 / `ICopy` 值类 | `get()` 副本 + `set()` 整值写回  | **无**（语言"参数复制"规则给的） | 无                                              |
| `Imm`                   | `get()` 只读引用                 | **无**                           | 无                                              |
| 可变引用·小高频         | `with(fun(mut v: T))` 作用域回调 | 有洞（把形参存出去）             | **"形参不得逃逸"的保守检查**（GC 前提，Inv-M5） |
| 可变引用·大低频可独占   | `Ownership<T>` 搬运              | **无**                           | 无（复用移交点）                                |
| ——                      | `lock()` 返回守卫 / 裸 `mut T`   | **拦不住**                       | 需编译期锁区间检查（**不在 v1**）               |

> 语言地基（spec 03）：**普通参数收到副本**（`mut` 参数只改局部副本）、**只有 `mut this` 别名
> 调用者对象**、**非左值链写入被拒绝**（`m.get().x = 1` 编译报 `E_MUTABILITY`）—— 这三条决定了
> 上表：值类那一档"无逃逸"是语言白送的，引用类型那一档必须自己拦。
>
> **写入口与"进来"是同一套约束**：上表"进来的规则"同样适用于 `with` 回调**内部**的每一次写入
> （含 `s.child.field = ...`）—— 见 Inv-M7：**可变**新值必须是"已带位 / 本临界区内新造的图 /
> `Ownership` move 结果"且双向无本地别名（Imm 豁免）。**构造与写，两条路一个检查。**
>
> `with` 形参的逃逸检查形态（保守、语法层、可判定，与 `Ownership` 全图新鲜性同类；评审精化）：
> - 只拦**引用类型**的字段链；**值拷贝的标量读取必须放行**（`println(s.count)` 这类纯读不能拦，否则误伤常见写法）；
> - **返回值也是逃逸通道**：回调只能返回 `ICopy`/标量，或返回不来自形参引用链的值；
> - 形参引用链不得赋给回调体外可达的左值、不得作为实参传给用户函数。

### 2.13 顺带发现（同一区域，非 `Mutex` 引入）

- **孤儿 arena**：arena 比线程活得久，而本地回收器是按**域**跑的 ⇒ **域退出后它的本地垃圾没有收集器**。
  两条路：域退出时收尾回收一次（简单），或全局收集器收编孤儿 arena 的本地对象。双层堆落地前必须定（D10）。
- **`nshared` 的读写纪律（评审后修正）**：换出**不减计数**（D6 单调），换入只写**本域 span** 的计数
  （Inv-M4 保证单写者），所以 `nshared` 的写永远是**本域串行**的 ⇒ **普通自增/自减即可，不需要原子操作**
  （留着作防御也无妨，但不构成理由）。计数 vs 单调标志的选择见 D9。
- **本地收集与全局收集互斥（免费的正确性护栏）**：全局收集要求**全停**，本地收集要求**本域在跑**
  ⇒ 两者永不同时发生。这条保证了"本地回收可以先于任何全局侧改动落地"（见 §4 顺序约束）。
  ⚠️ **但它有隐藏代价**：全局停世界要等每个 worker 到达安全点，而在做本地收集的 worker
  **不在安全点** ⇒ **全局 STW 的到达延迟会被拉长最多一次本地收集的时长**。两个暂停指标之间存在耦合，
  验收时必须**分别度量**（§5）。

### 2.14 共享区分配子系统（原稿缺的一块，M2 开工即需）

§2.3 / §2.12 / B2 多处依赖"复制进共享区""唯一引用的新对象直接在共享区分配""已划归共享的 span"，
但**共享堆的分配路径全文没有设计**，里程碑里也没有位置。最低限度先定（并写明是**临时形态**）：

| 问题                           | M2 的临时形态                                                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 共享区是什么                   | **复用现有 span 堆**：共享对象与本地对象的 span 物理相同，只按 `shared` 位区分归属 —— 这就是"逻辑分区"，所以 M2 **不需要新分配器**，只需要"置位" |
| "直接在共享区分配"             | 照常从本域 arena 分配 + **立即置位**（对象物理在本域 span、逻辑属共享侧）。与"物理分区（搬进共享 span）"的区别见 §2.8                            |
| 复制进共享区（值类 / `ICopy`） | 在**本域**分配副本 + 置位。**"按值复制以隔离发送方后续修改"这条语义作用不能省**（不是简单用置位顶替）                                            |
| 并发安全                       | 置位只在本域线程做（Inv-M4）⇒ 无需新锁、无需跨域协调                                                                                             |
| 与 malloc 大对象路径的关系     | 大对象（>512B）仍在 malloc 堆，用 `GCHeader.shared` 表示共享侧；穿透与释放规则见 §2.5 / §2.6                                                     |

**明确推迟**：真正的"物理共享 span 池"（跨域共享的空闲链、并发安全、与 malloc 路径合并）留到物理提升阶段（D7）。

## 4. 里程碑

> **编号说明**：原 M6（全局收窄）已随方案 F **取消**——全局收集器保持全量语义，其唯一改动
> （预算拆分）并入 M4；原 M7（文档收口）顺位为 M6。finalizer 相关交付随 native-arrays 全部删除。

**顺序约束（硬，决定里程碑次序）**

1. **M2（写点提升）必须先于 M4/M5**：本地 span 一旦出现带位对象，它们的 `shared` 位就必须已经是准的（§2.9）。
2. **M3（GC_VERIFY 断言）先于 M4**：本地回收上线前，Inv-S1/S2（正向闭包）的运行时兜底先就位。
3. **M4 不需要任何全局侧前置**：本地收集（要求本域在跑）与全局收集（要求全停）**互斥**，
   且全局保持全量语义（M4–M5 期间它自然兜底）—— 免费的正确性护栏（§2.13）。

### M0 — 前置审计与检查器（P1–P3、P5、P6）
- 交付：检查器规则 + **全仓 40 处**（主仓 34 + `others/libpenguin-esl` 6）ISync 实现者审计表
  （字段 / 谁引用 / 跨线程实际路径 / 能否退回单域）；**或**在封闭性声明里写明 `others/` 不在强制范围；
  **最简 `Mutex<T>`**（P6/D13：锁 + `with`/`set` + 值语义 API，不含守卫）
- 验收：清单外无法构造跨线程引用（检查器拒绝 + 反向用例）；审计表归档（按 §8.1 应用进设计文档）
- 风险：检查器工作量不确定（可能牵动 `SemanticClassifyValueTypes` / `SemanticInterfaces`）

### M1 — 位与计数落地（**不改变任何行为**）

### M2 — 移交点置位 + **写点提升** + 共享区分配（临时形态）
- 交付：
  ① §10.3 五类移交点按 §2.3 / §2.12 置位；
  ② **写点提升**（§2.9：从**新值**出发、遇已带位即停、worklist 迭代）接到**所有共享容器的写入口**
  （`Mutex.with/set`、通道 `push`、`Ownership` 移交、结果容器 `complete()`）+ **Inv-M7 的取值约束**；
  ③ **共享区分配临时形态**（§2.14：本域 arena 分配 + 立即置位；值类走"复制 + 置位"，复制隔离发送方的语义不能省）
- 验收：
  ① 流经通道/锁的对象**及其闭包**全部带位（计数器断言 + `nshared` 计数正确）；
  ② **空手（无写入）的 `with()` 提升成本为 0**（计数器断言；不得随载荷图规模增长 ——
  这正是"出口全图扫描"方案过不了的断言）；
  ③ `new Holder(localThing)`、`L.f = v; s.buffer = v`（可变新值先落本地字段再进共享）等形状被检查器拒绝（负向用例）；
  ④ 正向：`s.buffer = new ...`、`s.buffer = own.move()`、**Imm 带本地别名**全部放行
- 风险：中高（漏一个写入口 = 漏标，症状是延迟的误释放）
- （注：**换入对象的"本地回收下存活"专项挪到 M5** —— M2 阶段没有本地收集器，全局全量兜底使该断言恒真，验不出东西）

### M3 — GC_VERIFY 断言（Inv-S1/S2/S8 的运行时兜底）
- 交付：
  ① `GC_VERIFY` 的 **Inv-S1/S2 断言**（正向跨色边扫描：带位对象不得指向未带位对象）——
  **只在全局 STW 期跑**（本地收集期读带位对象的字段本身就与其他域的持锁写并发，断言自己就有数据竞争）；

  ③ **外部先例性质核对（一次性，约半天）**：对照 ORCA（ESOP'18 的 soundness 性质）与
  Lattice（六性质：phase 单调 / 堆分离 / 值隔离 / 消费性 freeze / forge soundness / thaw 独立）
  逐条核对我们的 Inv 集覆盖面，缺的补进 `GC_VERIFY` 或文档（unsafe 层例外见 §2.7）
- 验收：负向用例（带位对象被塞进未带位子对象——人为构造）被断言抓住；正向用例全绿
- 风险：低中

> 洞 1/洞 2/REFARR 链/共享保留/全局一致）全绿。

> **实现期补充的设计决定（2026-10-19，原稿缺口）**：
> 1. **span 域绑定**——原稿的"span 集合限定为本域"隐含 span 有域归属，但现状的退役 span 进**全局池**，
>    refill 跨域复用后同一 span 的槽会混多域对象，"本域 span 集合"无从谈起。决定：**span 从被取用
>    classed 起绑定取用它的域**，退役进**本域池**（GtArena 增 dom_partial/dom_full），refill 优先取
>    本域池；只有**完全空**的 span（sweep 整块回收）回全局 empty 池供任意域再取。域绑定 + Inv-S5
>    一起闭合了并发正确性：本地标记永远不会灰化别域的 span，无跨域位图写。
> 2. **M4 分两步**：M4a（本地回收算法，全局停止协议下触发，标记用 header.marked 而非 span 位图——
>    绕开两收集器的位图复用问题，保守根 = 全套根 + 叶子规则"非本域未带位对象跳过"（Inv-S5 下与
>    精确本域根等价）；M4b（按域停止协议——poll gate 分域化，编译器发射侧配合）。
> 3. **大对象穿透用 marked 防重**（本地回收记录穿透的大对象列表，结束统一清 marked——残留会让
>    下次回收把活对象误判"已处理"而漏标其子图）。

- 交付：
  ① 按域配额触发；**预算拆分**：本地分配不推全局 goal，带位槽字节（`nshared` × slot）从本地配额
  剔除计入共享预算；本地回收后 live 折进全局 unified goal 重算；
  ② **根集合完备性（评审洞 1）**：本域帧链（含停驻栈）+ 本域隔离环 + **全局根/保守 region 注册表的
  本域过滤**；
  ③ **大对象"不释放但要穿透"（评审洞 2）**：从本地根可达的大对象读 refmap 继续标记它指向的本域
  span 对象（中转链不断）；带位对象不当根不穿透（Inv-S8）；
  ④ **按域停止协议**：现有 poll gate 是**全局一个字**，本地回收要"只停本域" ⇒ 需要**每域 gate +
  全局/域两级停止 + 全局收集的多域会合**（这是一整套协议分域化，不是"接口预留"）；
  ⑤ **位图所有权纪律**：本地回收与全局回收共用同一套 `gray_bits`/`black_bits` ⇒ 本地回收结束前
  必须把**本域 span 的灰黑位清干净**，否则全局标记会读到残留位而误判；
  ⑥ 域退出时的收尾回收（孤儿 arena，D10）
- 验收：
  ① **本地回收期间其他 worker 不被停**（时间戳/计数器断言 + TSan）；
  ② 纯本地垃圾被本地回收（`gc_info` 回落）；**位图无残留**（回收后全量为 0 的断言）；
  ③ **洞 1 专项**：封闭类全局变量 / scheduler 容器缓冲引用的本域对象，在本地回收后仍存活；
  ④ **洞 2 专项**："帧 → 大对象 → 本地 span 对象"的中转链，本地回收不误收；
  ⑤ 全套件 + mt 套件绿
- 风险：中高（停世界协议分域化 + 根集合完备性是原稿漏估的工作量）

**性能验收（对照 §1 基线）**

| 指标                    | 目标                                                                                                                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **全局收集次数**        | 同负载下显著下降（本地 churn 不再推全局 goal）；**对照 §1 基线：19 次 / GC 5.73 s（mark 4.98 s + sweep 0.75 s）**。幅度取决于共享 churn 占比——`Mutex` 换缓冲/大消息占比高的负载收益小（§2.11） |
| 全局单次暂停            | ≈ 今天（~300 ms，全量标记）—— **方案 F 明确不优化这项**，只取频率                                                                                                                              |
| 本地回收暂停            | 与**本域**存活集成正比；且不阻塞其他 worker                                                                                                                                                    |
| **全局 STW 的到达延迟** | **必须单独度量**：全局收集要等每个 worker 到安全点，而正在做本地收集的 worker 不在安全点 ⇒ 到达延迟会被**拉长最多一次本地收集的时长**。两个暂停指标之间存在隐藏耦合                            |
| 空手 `with()` 的记账    | 恒为 0（不随载荷图规模增长）—— 这条同时是"出口扫描"方案的否决依据（§2.9）                                                                                                                      |
| 本地堆不被饿死          | 本地配额可靠触发；**带位字节已从本地配额剔除**（否则本地堆被收不动的对象占满 → 空转抖动）                                                                                                      |
| **共享侧监控**          | `gc_info`/`GC_PROFILE` 新增"带位字节数 / 共享占比 / 换出批次数"计数器（支撑上表全部实测；对照 Java 分代对 premature promotion 的监控经验）                                                     |
| 回归红线                | 单线程/顺序负载（编译器自编译）性能与内存不得下降                                                                                                                                              |

## 6. 风险与回退

| 风险                                                          | 后果                                                | 处置                                                                             |
| ------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Inv-S1 漏项**（最危险）                                     | 本地回收误收带位对象引用的子图 → 崩溃在别处         | ① 检查器静态保证优先（D1-b）；② `GC_VERIFY` 断言（M3）；③ 总开关回退             |
| **本地根集合不完备（洞 1）**                                  | 全局变量/容器缓冲引用的本地对象被本地误收           | M4 交付②（全局根/保守 region 的本域过滤）+ 专项用例                              |
| **大对象中转断链（洞 2）**                                    | "帧 → 大对象 → 本地对象"链上的对象被本地误收        | M4 交付③（大对象不释放但要穿透）+ 专项用例                                       |
| 本地回收频率失控                                              | 本地回收变高频抖动                                  | 配额调参；复用 young 预算的实测方法论（扫参数出拐点）                            |
| **带位字节挤占本地配额**                                      | 本地堆被收不动的带位对象占满 → 本地回收空转         | M4 交付①（`nshared` × slot 从本地配额剔除计入共享预算）                          |
| **共享 churn 占比高**                                         | 全局收集频率收益不及预期（§2.11 的换缓冲模式）      | 规范判据引导到 `Ownership`；载荷峰值纳入共享预算；`GC_PROFILE` 实测占比再决定 D7 |
| 碎片（`shared` 对象散在本地 span）                            | 整块回收失效                                        | `nshared` 计数 + 纯本地 span 的整块回收；必要时 M5 之后走物理提升                |
| 检查器改动牵动过大                                            | P1 拖期                                             | 先做"只拒绝明显非法的载荷"（保守），逐步收紧                                     |
| **写入口漏一个**（`with`/`push`/`complete`/`Ownership` 移交） | 换入的对象拿不到 `shared` 位 → 被本域本地收集误释放 | M2 验收逐个覆盖；`GC_VERIFY` 的 Inv-S1/S2 断言；回退开关                         |
| **`Mutex` 载荷 churn**（换缓冲模式）                          | 共享堆膨胀、全局收集频率回升                        | 规范判据引导到 `Ownership` 搬运；把载荷峰值纳入共享堆预算                        |
| **按域停世界协议被低估**                                      | "只停本域"要每域 gate + 两级停止 + 全局多域会合     | M4 交付④；工作量已计入 §10                                                       |
| **位图残留**                                                  | 本地收集后残留灰黑位 ⇒ 全局标记误判                 | M4 交付⑤（回收后清零断言）                                                       |

**两种分区：物理与逻辑（2026-10-16 补充）**

#### B2 → **替换** `### 10.4 提升怎么做` 整节

````markdown
### 10.4 提升怎么做：三策略分流

移交点（§10.3）上"把值放进共享区"按**对象形状**分流：

| 对象形状                                | 手段                                                                                                                                                                       | 理由                                                               |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 值类 / `ICopy` / 扁平不可变（`string`） | **按值复制**，不保持身份                                                                                                                                                   | O(1)（字符串是扁平结构）；复制隔离发送方的后续修改                 |
| **`Imm(T)` 的引用图**（深不可变，§4.1） | **原地置 `shared` 位**（§10.9）                                                                                                                                            | 绕开深拷贝：引用图的深拷贝要同时处理别名、身份分裂与环，实际做不到 |
| **可变对象**                            | **不得"就地"移交**（本地仍有别名时置位 = 数据竞争）：先在临界区内新造（分配即置位，§10.12）；或走 `Ownership`（同域零拷贝 / 跨域接收方复制，§9.5）；再无路则**检查器拒绝** | 已移交的可变对象必须带位，此后只能经同步容器访问（Inv-S3）         |

唯一引用的新对象（创建点上下文对象、`Ownership` 包装体）走"**直接在共享区分配**"
（临时形态 = 本域分配 + 立即置位，§10.9），不参与上面的分流。

**为什么 `Imm` 是"原地置位"的硬前提**（两条，缺一不可）：

1. **数据竞争**：把可变对象标成共享，别的线程就能通过共享对象读写它，而本地线程仍无锁地改同一个对象；
2. **撕裂读 ⇒ 漏标 ⇒ 误释放**：本地回收器要读 `shared` 对象的字段来标记；对象可变而别的线程在写时，
   会读到半新半旧的指针，漏掉一个引用就会在下一轮把活对象当垃圾收掉。

这与 §11 已否决的"动态冻结"同源 —— **可变性是逐绑定的权限而不是对象状态，别名集合运行时不可枚举** ——
所以判据必须是**静态的 `Imm(T)`**（§4.1 已经算得出来），不能靠运行时观察。

**原地置位留下的唯一漏洞：闭包跨域。** 需要的不变量是
**Inv-S1：带位对象的整个可达闭包都带位**（§10.6）。三种保证方式见 §10.10，
**推荐静态保证**：只允许"闭包必然在本域构造"的 `Imm` 图走这条路，其余退回复制或共享区分配 ——
分析不精确只损失性能，不损失正确性。

**写入口的取值约束**：写进共享对象的**可变**新值只能是"**已带位 / 本临界区内新分配的图 /
`Ownership` move 结果**"三者之一，且**全图双向无本地别名**（Imm 豁免）（Inv-M7，§10.12 / 计划 §2.9）。

**顺带要求（不变）**：程序里不能有依赖"同一个对象在不同线程里身份相同"的代码（按地址哈希、
`__object_id` 比较之类）。审计结论写进规范。
````

只要求**单向**闭合：带位 ⇒ 可达者带位。反向边（本地 → 带位）合法——全局回收器保持全量标记

````markdown
### 10.12 共享容器（`Mutex<T>` / 通道）与 GC 的耦合（2026-10-16）

`Mutex<T>` 对**任意 `T`** 都是 `Sync`：约束不在 `T` 的类型上，而在**载荷怎么进来**与
**访问权怎么出去**两个时刻（构造/写入 = §10.3 第 2 条移交点）。

**提升在"写点"，不在"出口"**

❌ **出口全图扫描不可行**：要发现挂在已带位对象下面的新对象，就必须**穿透**已带位对象继续走 ⇒
① 空手 `with()` 的成本变成 O(整个载荷图)；② 一张图可以同时挂进两个容器，穿透读它的字段会与其他
锁持有者的写并发 ⇒ 撕裂读 ⇒ 漏标 ⇒ 误释放（"锁内完成"只保护本锁的载荷，保护不了别人临界区里的部分）。

✅ **写点提升**：从**新值**出发、遇已带位即停。新值只有本人持有（读它无并发）；已带位对象的整个
闭包都已带位（Inv-S1），**不必读它的字段** ⇒ 无撕裂读。**空手 `with()` 的成本为 0**。

| 编号       | 不变量                                                                                                                                                                                                      |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Inv-M1** | 写入口必须从**新值**出发做提升（`new` 图递归；遇已带位即停）                                                                                                                                                |
| **Inv-M2** | 提升在**锁内**完成（**不是**出口全图扫描）                                                                                                                                                                  |
| **Inv-M3** | 提升覆盖新值的**整个闭包**（`new Holder(localThing)` 要连 `localThing` 一起判）                                                                                                                             |
| **Inv-M4** | 提升只触及**本域 span** 的对象（跨域引用必经移交点、已带位）⇒ 无跨域位写入竞态                                                                                                                              |
| **Inv-M5** | 访问权不得逃出临界区（**GC 正确性前提**）                                                                                                                                                                   |
| **Inv-M6** | 构造时的初始载荷走同一条路径（构造 = 第一次写）                                                                                                                                                             |
| **Inv-M7** | 写进共享对象的**可变**新值只能是"**已带位 / 本临界区内新分配的图 / `Ownership` move 结果**"三者之一，且**全图双向无本地别名**（入边反例：先 `L.f = v` 再 `s.buffer = v`，拒绝；Imm 豁免——不可变无数据竞争） |

实现形态：① **分配点提升**（推荐起步，零插桩）：临界区专用链表，或"临界区内分配即置位"
（TLS 深度计数；已知代价：临界区内未进载荷的临时对象也被置位成共享垃圾，可后补"出口只提升
载荷直接字段指向的区间内新值"来精化）；② 编译器插桩（需要 "shared-referenced" 效应，与 Inv-M5 同机制）。
**覆盖范围**：`Mutex` 的 `with`/`set`、通道的 `push`、`Ownership` 移交、结果容器 `complete()` —— 一条通则。

**共享对象的可达性：全局保持全量标记，不需要任何发现机制**

全局回收器保持今天的全量标记（§10.8 全套根、穿透一切对象）。因此**反向边合法**：
"接收方把消息存进本地容器"（缓存/批处理/关联/窗口——通道消费者的日常）——全量标记从
帧 → 本地对象 → 带位消息 一路穿透，存活无死角。被否决的路线留档：❌ 双向闭合（把日常写法变非法，
级联提升需要枚举引用者闭包 = 别名集合不可枚举）；❌ 同步对象注册表（救不了非 Sync 对象；
永不注销 = 全量泄漏）；❌ 本地上报 + epoch（陈旧窗口）；❌ STW 自扫带位当根（永久钉住 = 泄漏）。

**换出：共享垃圾只归全局收集者。** 旧载荷保持 `shared` 位（无降级）⇒ 本地收集器永不回收它 ⇒
只有全局收集能收。"锁内换缓冲"的 churn 全部落在共享堆。规范判据：**"会被另一个线程读到吗？
会 → `Mutex`/通道；不会 → `Ownership` 搬走"**，外加"图多大 / 访问多频繁"（跨域 `Ownership` 是
**接收方复制**，§9.5 ⇒ "搬走"的成本也是一次拷贝）。

**本地收集器既不把带位对象当根、也不穿透它们**（Inv-S8）；它们由全局收集器保活与释放。
清扫零用户代码（IMemoryDispose 已删除），无 finalizer 时序问题。

**访问面（与 Inv-M5 配套）**：四档 = 值语义（`ICopy`）/ `Imm` 只读 / `with` 作用域回调 /
`Ownership` 搬运；**不提供** `lock()` → 守卫 / 裸 `mut T`（语言没有生命周期）。
形参逃逸检查：只拦**引用类型**的字段链（**放行值拷贝的标量读**，`println(s.count)` 不能误伤）、
**返回值也是逃逸通道**、不得赋给体外可达左值或传给用户函数。
**写入口与"进来"是同一套约束**：上表"进来的规则"同样适用于 `with` **内部**的每次写入（Inv-M7）。
````

  - **OCaml 5**：per-domain minor heap（本地回收只停本域）+ 共享 major 的两级架构的工业先例；
    其 major 用并发标记 + 写屏障——我们选全量 STW，是"不要写屏障"的第三种换法。
  - **Erlang/BEAM**：per-process GC + off-heap binary（>64KB 全局管理）≈ 我们"大对象归全局"；
    其消息全复制的代价是我们 Imm 零拷贝置位要避免的（见 §2.11 留档）。
  - **Rust `Send`/`Sync`、Swift `Sendable`/actor isolation**：静态排除共享错误的判据先例
    （`Sync` 连命名都同源）；Swift 的 `@unchecked Sendable` 逃生舱教训——我们的对应逃生舱
    是 `Ownership`（显式交出），不再开后门。
  - **GHC**：per-capability nursery + statics/CAF 的根完备性问题 ↔ 我们的洞 1（本地根必须含
    全局根/保守 region 的本域过滤）。
  - **无先例的三处（= 风险所在）**：Imm 图零拷贝置位、共享侧"全量但低频"、静态判据 + 逐对象
    逻辑分区（span 不物理分家）——恰对应 M2/M4/M5 三个高风险里程碑，M3 的性质核对因此必要。

## 五场景性能矩阵评估（2026-10-23 round 18，bench/gcmat/）

新 tb 套件（bench/gcmat/，五场景×classic/mt4/mt8×老GC/双层/串并行/LOCAL/LMT/NOGC/RELAX，
全部 checksum 校验，results-20261023.tsv）。上一代 tb 全配置无差异的根因：默认
EMPEROR_GC_YOUNG=128MB，总分配量不足一次触发线——GC 根本没跑。紧凑堆
（YOUNG=8MB）下才拉开差异。

**正确性（矩阵即取证）：**
- **mt 帧链竞态**（新哨兵 MtGcFrameChainRace.md，6c7d16bb）：mt+频繁GC+长寿命轮转
  array<u8> 帧槽+多生产者 Fifo → exit 134（CORRUPT REF-MAP ctx=frame-mark，map 恒指
  协程栈顶 0x…fffffba0）或 exit 63（lost-wake at=NOWHERE）。**布局敏感**：重链前 9/9 崩、
  加分相计时重链后 0/10、8T 不绑核 ~50-85%/次。矩阵里 MIXED(n crash) 散布于
  app/large/shared 的 mt 格。嫌疑：scheduler.c parked_link 窗口 / epoch gather 覆盖 /
  销毁协程悬挂链；classic 与 NOGC 全绿。
- **LMT 取证升级**：tbm_live 下 LOCAL_MT=1 三次全 WRONG checksum（不止丢交接，常驻
  森林也丢）；shared/app 直接崩。guard 保持默认关是正确的。
- classic 全绿；双层 vs 老 GC 在 classic 所有场景逐字节同级（基础设施零开销 ✓）。

**性能（中位数，紧凑堆）：**
1. **并行标记在链式 live 上是 5.7× 纯亏**：tbm_live mt4 mark 1317ms vs 串行 229ms
   （classic 225ms）——链只能串行走，4 worker 抢 _gt_qmu/gray 位图 cache line；墙钟
   -26%（4949→3916），mt8 同样 -27%。宽图（tbm_shared）小赢 ~6%（清扫分片受益）。
   **建议：PAR_MARK 默认翻回串行**，或把逐槽 atomic 队列改回 span 批次认领。
2. **本地收集器在全矩阵无一胜绩**：全局 GC 优化后已太便宜（tbm_local 163 fulls 共
   60ms），LOCAL=N 的固定小额周期 ×17000 次反而更贵（+24%）；live 重则是灾难
   （L16：每 128KiB churn 重标 12.6MB 森林 ×8161 次 = **11× 变慢**）。需要 live 感知
   配额（quota ∝ live）才有存在价值；保持默认关。
3. **mt 隐性 GC 成本 ~100-150ms/周期**：tbm_local mt4 墙钟 7442 vs NOGC 4961 差 2.5s，
   但 gc_total 只计 156ms/26 周期——间接停顿（gate 窗口慢路径 + epoch gather）是
   直接周期时间的 16 倍。mt 目标超额 4×（live_peak 16.1 vs classic 4.0MB，fulls 11 vs
   79）。这两项是 mt GC 的真瓶颈，比标记并行化重要得多。
4. mt 内核本身：CPU 密集协程负载比 classic 慢 1.7-2.9×（NOGC 地板 4961 vs 2991）；
   分配吞吐负载（tbm_large）反而 3.3× 快。tbm_large 全配置无差异（大对象路径不敏感）。
5. RELAX（默认旋钮）下所有场景 GC <5%，配置选择无关紧要——面向用户的默认体验由
   young 预算主导，而不是收集器算法。

**结论**：双层地基（shared 位/域/提升）健全且零开销，写点提升在通道负载下工作正常
（shared mt promote_calls=1.92M，classic 单域早退 0 开销）；但两个大赌注——默认开的
并行标记、域本地收集——当前都是净负收益。下一步优先级：mt 隐性停顿与目标超额 >
帧链竞态根因 > PAR_MARK 默认翻转/重造 > LOCAL live 感知配额。
