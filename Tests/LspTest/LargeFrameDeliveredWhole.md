# LargeFrameDeliveredWhole
## Description
Bug #5 sentinel (batch 5 handover, mitigated in bugfix round 2): a documentSymbol response LARGER than the 64KB stdout pipe buffer (123182 bytes on the wire). The old StdioStream write path parked the writer coroutine on POLLOUT when the pipe filled mid-frame; after the fd wake the coroutine never retried the remaining write (strace-verified: zero write() calls after the POLLOUT wake), silently truncating the frame at a 64K boundary — the client then blocked forever reading a Content-Length it could never receive, and every later response (queries included) was lost: the "EP-scale didOpen loses responses" shape. Reproduced with EMPEROR_GC_DISABLE=1 as well (not a GC scan miss; the exact ucontext/requeue mechanism stays filed with the scheduler batch). Mitigation: `_emperor_write_fd` POSIX now uses the Windows model — a BLOCKING loop-write IS the backpressure for the strictly-ordered single writer (core_builtin.c); StdioStream's park loop remains but a real pipe never reaches it. This test holds 600 functions (~100KB symbol response): the golden demands the FULL byte stream through the final shutdown response — any frame truncation loses the tail and fails the match. Honest scope note (verified by relinking the pre-mitigation server): the test runner's stdout consumer drains the pipe as fast as the server writes, so the pipe never fills and the buggy POLLOUT park path is NOT exercised under the runner — the pre-mitigation server also passes this test. The sentinel therefore locks the functional guarantee (a >64KB response arrives whole) against any future writer regression; reproducing the park-resume defect itself requires a slow consumer (the /tmp/bfx4/strace_driver.py shape: a client that stops reading mid-frame). Golden recorded from the mitigated server (only Content-Length digits wildcarded). Server built by 'make lsp'.
