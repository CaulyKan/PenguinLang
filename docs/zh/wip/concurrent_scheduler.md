## 摘要

目标是把现在的单线程协程调度器扩展到多核，而**用户程序里不出现任何线程概念**。三条原则：

1. **调度完全自动**：哪个协程在哪个线程上跑，由编译器和运行时决定。
2. **用户不关心线程**：语言不提供"在某个线程上启动"这类接口；并发正确性不依赖用户自觉。
3. **正确性优先于效率**：宁可完全不并行，也不接受一个可能产生数据竞争的优化。

核心机制是一个编译期的**封闭分析**：每个协程在创建点被静态分类为**可偷**（还没开始跑的
新协程可以被别的线程领走）或**固定**（只能在出生线程上跑）。分类依据是类型层面的**共享
格**：值类型、不可变类型、自带锁的类型可以跨线程；其余引用类型一律关在单线程里；真的
需要把引用交给别的线程，走显式的 `Ownership<T>`。

本文的五个关键决定：

| # | 决定 | 一句话理由 |
|---|---|---|
| A | **协程一旦开始运行，就永远固定在那个线程**（只有还没跑过的新协程能被别的线程领走） | 协程自己栈上的临时变量永远不会跑到别的线程去，"它停顿时手里攥着什么"就不需要分析了 |
| B | **时间分两层：tick 与 delta tick。delta tick 内谁就绪谁就接着跑（不等别人），只在 delta 边界（收敛点）碰头** | delta 内顺序本来就没有语义依据；把"让出"强行解释成"放弃一整个 delta"只会凭空制造顺序依赖 |
| C | 语言不承诺跨 delta 的行为确定；想要确定的结果，就把**跨协程共享的可变数据**放进"延迟提交"构件（信号、延迟通道、事件） | 延迟提交让"本 delta 的动作"与先后顺序无关，而且让"延迟"变成构件的属性而不是调度机制的属性 |
| D | 线程之间**不搬运对象**，只在明确的"移交点"把值复制进共享区 | 垃圾回收因此不需要写屏障（见第 10 章） |
| E | **只有"所有协程都结束"才退出**；只要还有协程停靠着，程序就继续等（等不到就静静挂着） | 不试图区分"正常等待"与"卡住"，先要一个简单、不会误杀服务型程序的规则 |

## 0. 先读这一节：协程、时间、让出

### 0.1 协程和线程的区别

| | 线程 | 协程 |
|---|---|---|
| 谁决定切换 | 操作系统，任意时刻抢占 | 协程自己，只在写明的地方让出 |
| 切换时保留什么 | 由操作系统保存现场 | 调度器保存这个协程的栈和现场 |
| 数量级 | 几百到几千 | 几万到几十万 |
| 需要锁吗 | 需要（别的线程随时可能改你正在读的数据） | 不需要（没有谁能在两行代码之间插进来） |

关键差别是**不会被打断**：一个协程从"让出点"到下一个"让出点"之间的代码是连续执行的，
中间不会有别人插手。所以现在的语言里没有任何锁，通道和事件都是普通类
（`EmperorPenguin/std/penguin/scheduler.penguin`）。多线程要解决的问题正是：两个协程真的
同时在两个 CPU 上跑之后，"不会被打断"这条性质只在**一个线程之内**成立。

协程有自己的**栈**（存放局部变量和函数调用链的内存）：`EmperorPenguin/std/c/scheduler.c`
用 ucontext（POSIX）或 Win32 fiber 实现创建、切换、销毁，每个协程一块 mmap 分配的 32MB 栈
（`scheduler.c:71-79`）。因为这块栈是独立保留的，协程可以停在任意深度的函数调用里，下次
接着跑。

### 0.2 时间的两层：tick 与 delta tick

这个语言用来做**硬件仿真**。仿真时间（虚拟时钟）是假的，它由调度器记账，分两层：

- **tick**：仿真时间的单位。`wait 5;` 表示等仿真时间前进 5 个 tick；定时器按 tick 记截止点。
  虚拟时钟**只在 delta 边界推进**，一次推进到下一个到期的定时器截止点。
- **delta tick**：**不推进仿真时间**的最小推进单位——同一 tick 上的一次**收敛阶段**：从上
  一次收敛点开始，把所有就绪的协程跑到全都停靠或结束，然后收敛。`wait;` 表示"等本 delta
  收敛，在下一个 delta tick 接着跑"（仿真时间不动）。

一个 tick 里可以连续发生很多个 delta tick（每写一次 `wait;` 就多一个），直到再也没有事情
可做，仿真时间才前进到下一个定时器截止点。某件事的**时间位置**由一对数决定：
（第几个 tick，该 tick 内第几个 delta）。

**delta 内规则**：谁就绪谁就接着跑，不等别人。

- 一个协程停靠后，只要它等的条件成立（比如通道里来了东西），它在**当前 delta tick 之内**
  就会被接着跑下去，不需要等到收敛点。
- `wait;` / `wait 0;` 把协程从本 delta 的就绪集合里摘出去，等本 delta 收敛之后才重新就绪；
  `wait -1;`（负数，只让出执行权）**不摘出去**，它只是排到队尾，调度器可以不做任何判断就
  再轮到它。
- 新创建的协程在**当前 delta tick** 就可以跑。
- 一个 delta tick 里同一个协程可以跑很多次（只要它反复就绪）。

**delta 边界（收敛点）规则**：再没有任何协程处于就绪状态时（大家都结束了，或者都在等
条件/等时间/要求"再来一个 delta"），由一条线程依次做以下判断（这一小段是单线程的，并且
对全部线程构成一道内存屏障——屏障之前的一切写入，屏障之后全部可见）：

1. **提交延迟写**：把本 delta 挂起的写入按固定顺序提交（见 6.4 节）。
2. **触发到期的定时器**：截止点 ≤ 当前 tick 的定时器生效，唤醒等它的协程。
3. **还有活吗**：只要第 1、2 步让任何协程变就绪，**或者**本 delta 里有人登记过"要下一个
   delta tick"（写过 `wait;` / `wait 0;`）——就不推进仿真时间，直接开始下一个 delta tick。
4. **非阻塞探测一次外部输入**（fd）：有就绪事件就唤醒对应协程，开始下一个 delta tick。
   （这步放在推进时间之前，保证外部事件永远不会被定时器或 delta 风暴饿死。）
5. **只剩"等时间"的**：把虚拟时钟推进到最早的定时器截止点，触发定时器（回到第 2 步的
   效果），开始下一个 delta tick。
6. **只剩"等外部输入"的**：阻塞在 `poll` 上等外部事件，事件到达 → 下一个 delta tick。
7. **所有协程都结束了** → 退出；否则挂着（见 7.4 节）。

第 3 步里"`wait;` 登记下一个 delta"这一条的意思是：**`wait;` 给当前 tick 设了卡，仿真时间
不许从它身上跳过去**。所以"每次让出一下再重试"的循环会把时间牢牢钉住（0.3 节）。

今天实现里的 delta 比上面"浅"：它把就绪队列扫一遍就当作一次收敛（收敛是不完全的，让出
被解释成"排到下一个 delta"）。计划中的调度器把它改成完全收敛。这个差别是第 6 章的主题。

### 0.3 让出（`wait`）的几种意思

`wait` 就是让出。它有几种写法：

| 写法 | 含义 |
|---|---|
| `wait;` / `wait 0;` | **推进一个 delta tick**：等本 delta 收敛，在下一个 delta 接着跑。仿真时间不动，且给当前 tick 设卡 |
| `wait 5;` | 等仿真时间前进 5 个 tick（要等 delta 边界推进时钟） |
| `wait -1;`（负数） | **只让出执行权**：不进入下一个 delta，协程仍在当前 delta 内排队，调度器可以立刻再轮到它。负数的具体大小不表示别的含义 |
| `wait ch` / `wait f` / `wait ev` | 等条件（通道有数据 / 协程算完 / 事件发生）；条件一满足就在**当前 delta 内**接着跑 |

三种东西别混：`wait;`（= `wait 0;`）是"这个 delta 我干完了，下一个 delta 再叫我"，而且它
**给当前 tick 设卡**；`wait n;` 是等仿真时间；负数只让出执行权（只是排到队尾，不代表时间
推进，也不给 tick 设卡）；其余是"等某个条件"。只有"推进 delta"和"等时间"会跨过收敛点；
负数和条件等待都只在同一个 delta 内调动执行顺序。

两个**已删除的写法**（M0 已落地，见第 15 章）：`wait n tick;`（带 `tick` 的长写法——语法
产生式已删，只留 `wait n;`，见 2.2 节）；`wait cond` / `wait change(x)`（等任意布尔条件、等
某个值变化——它们**没有唤醒源**：写条件的协程不知道谁在等它，只能每个 delta 边界全体重查
一遍，无法实现"条件一满足就接着跑"；两编译器 binder 现一律以 E_TYPE_MISMATCH 拒绝。需要
等状态的场景用通道/事件/信号表达，见 8.2 节）。

**"等条件"必须写成条件等待（通道/事件/信号），不能靠"让出一下再试一次"。** 两种"让出"都
会把时间钉死，只是方式不同：`wait -1;` 让协程一直就绪，本 delta 永远收敛不了；`wait;` 虽然
让本 delta 收敛，但它登记了"再来一个 delta"，而时钟不许越过当前 tick，于是时间停住。下面
这个程序在新语义下两种写法都结束不了（等时间的消费者永远醒不过来）；今天它能跑完（实测：
正常退出），因为今天的裸 `wait;` 不给 tick 设卡（2.2 节）：

```penguin
let ch : mut __builtin.Fifo<i64> = new __builtin.Fifo<i64>(1, new __builtin.FifoPolicy.backpressure());

initial {                                   // 生产者：写两个值，满了就等
    ch.write(1);
    while (ch.is_full()) { wait; }           // ← 必须改成"等通道不满"的条件等待（8.3 节）
    ch.write(2);
}

initial {                                   // 消费者：等 10 个 tick 才来取
    wait 10;
    let v : i64 = wait ch;
}
```

### 0.4 一个最小例子

```
initial {                 // 协程 A
    println("A1");
    wait;                 // 等于 wait 0：本 delta 收敛之后，在下一个 delta 继续
    println("A2");
}

initial {                 // 协程 B
    println("B1");
}
```

`initial` 块是程序的入口协程，按出现顺序创建（它们在第一个 delta 就能跑）。

| 时间位置 | 发生什么 |
|---|---|
| tick 0, delta 1 | A 打印 `A1` 后要求下一个 delta（A 本 delta 不再就绪）；B 打印 `B1` 后结束 |
| delta 边界 | 再没有就绪的协程（只剩 A 登记了下一个 delta）→ tick 0, delta 2 |
| tick 0, delta 2 | A 打印 `A2` 后结束 → 所有协程结束 → 程序退出 |

输出是 `A1 B1 A2`。把 `wait;` 换成 `wait -1;`（只让出执行权）的话输出还是 `A1 B1 A2`，但
时间位置不同：A 让出后立刻就能再被调度，所以 `A2` 和 `A1` 落在**同一个 delta** 里，整个
程序一个 delta 就跑完了。

## 1. 目标与"正确"的定义

### 1.1 三条原则

见摘要。补充一条推论：**放置（哪个协程去哪个线程）出错只损失并行度，转移（引用跨过线程
边界）出错才会产生数据竞争**。所以放置可以自动推断，转移必须显式声明（`Ownership<T>`，
第 9 章）。

### 1.2 承诺什么

- **无数据竞争**：任何一个非共享对象的可变访问，只发生在单个线程的执行流里。
- **无内存错误**：垃圾回收不会回收还活着的对象，也不会让指针失效（不搬运对象）。
- **不悬空**：一个对象不会在某个线程还在用它的时候被另一个线程的回收器释放。

### 1.3 不承诺什么

- **顺序确定性**：并行形态下，同一个 delta 内两个协程谁先跑是不确定的，因此任何依赖它的
  结果都不可依赖（见第 6 章）。
- **免死锁、免永久挂起**：卡住的程序不会报错，也不会自动结束，它就是一直等下去。调试
  工具将来可以加检测，语言本身不做承诺（见 7.4 节）。
- **免饥饿、公平**：某个协程不保证按比例得到执行机会。
- **单线程形态下"delta 内顺序"照旧不承诺**：默认的 sim 形态是单线程的，同一个 delta 内部
  的执行顺序仍然是调度器实现决定的，不是语言承诺（今天它稳定，是因为实现恰好用先进先出）。

### 1.4 确定性可以给到什么程度

虽然不承诺全局确定性，但可以给一个**可判定的子集**：程序只要满足"跨协程共享的可变数据
全部放在延迟提交构件里，并且每个通道只有一个等待者"，那么不仅**值**是确定的，连**某件事
发生在（第几个 tick，第几个 delta）**也是确定的（因为每一次跨协程传递都强制一个 delta 边
界，而 delta 边界只由"还有没有活"决定，与调度顺序无关）。这是第 6 章的核心结论，编译器能
诊断，测试工具能验证。

## 2. 现状（当前代码的真实行为）

### 2.1 协程与调度器

- 协程是**栈式**的：每个协程一块独立栈（`scheduler.c`，ucontext / Win32 fiber）。
- 调度**策略**（就绪队列、定时器、虚拟时钟、静止判定）是 Penguin 代码
  （`std/penguin/scheduler.penguin` 的 `__sched_run`）；C 侧只有上下文切换的微内核。
- 创建面是 `async f(args)`。编译器把它重写成：一个上下文对象 `__SpawnCtx_<n>`（字段就是
  各个参数）+ 一个结果容器（每个创建点一个类，字段是 `done` 和 `result`），子协程的入口
  执行 `f(...)` 之后把结果写进容器的 `complete()`（`SemanticBindExpressions.penguin`
  的 spawn 重写，约 `:2490-2560`）。
- **父协程是自己轮询结果容器的**：`wait f` 展开成 `IFuture.do_wait()`，它每个 delta 让出
  一次，醒来后读一次容器的 `done`/`result`（`scheduler.penguin:100-118`）。

### 2.2 今天的 delta（与第 6、7 章有关的部分）

- delta 内顺序是**先进先出**：`_sched_ready` 是普通链表队列（`scheduler.penguin:226-251`），
  依次出队执行（`:596-597`）——每个协程一个 delta 最多跑一次。
- **让出 = 排到下一个 delta**（`:615`）；新创建的协程进当前 delta 的队尾（`:618-620`）。
  也就是说今天的一个"delta"只是把就绪队列扫一遍，收敛是不完全的：即使条件马上成立，
  也要等到下一个 delta。
- **裸 `wait;` 与 `wait 0;` 机制不同，今天都在当前 tick 被服务**：`wait 0;` 登记"当前时刻"
  的定时器，给当前 tick 设卡（时钟不许跳过它）；裸 `wait;` 不设卡，但空闲时间跳跃以"本
  回合有活动"为门——裸 `wait;` 自身的唤醒即标记活动，服务它的回合不会被时钟跳过
  （`Tests/TimingTest/DeltaParkNotJumped.md` 钉住。把裸 `wait;` 统一降低成零截止定时器的
  设卡方案会压死 Fifo 背压写者——现行机制是活动门，不用设卡）。
- **带 `tick` 的长写法已删除**：语法里只留 `'wait' expression?`
  （`BabyPenguin/Parser/PenguinLang.g4:42`），`wait n` 是唯一的时长写法。负数写法
  （"只让出执行权"）**已实现**：两个新语义调度器都按运行期符号分支降低
  （原生 mt 侧 `_mt_wait_ticks`，BabyPenguin 侧 `_wait_ticks`——字面量与运行期求值
  同路）；经典调度器上负数仍走旧定时器路径（截止点在过去，下一轮即就绪）。
- **"本 delta 有没有活动"决定时钟能否前进**（`:648`）。活动的定义是：通道投递
  （`Fifo.deliver`，`:820`）、线语义通道的写入（`:990`、`:997`）、扇出（`:1341`）、事件广播
  （`Event.emit`，`:1536`）、以及一次成功的"等条件"（`do_wait` 拿到结果，`:113`）。
  **从通道里取值本身不算活动**（`try_poll` 只做 `dequeue`，没有调用活动计数）。
- 结束判定是"活动"驱动的：没有活动、没有协程结束、没有定时器、没有外部输入，就计算**静止
  指纹**（每个存活协程冻结栈的哈希按收养序合并），连续两个 delta 指纹相同即结束（`:694-702`）。

上面第 1、2、5 条描述的"浅 delta、让出排下一轮、静止指纹退出"已在新语义调度器（原生 mt +
BabyPenguin）中改掉：delta 完全收敛（0.2 节）、结束判定改"所有协程都结束"（7.4 节）；经典
调度器保留旧语义作为原生默认（见文首状态声明）。

### 2.3 delta 内顺序现在是确定的

今天同一个程序每次运行的 delta 内顺序完全一样（先进先出），测试因此可以逐字节断言输出。
要说清楚的是：**这是调度器实现的性质，不是语言承诺**。第 6 章会用一个今天就能跑的实验说
明，仅仅把两个协程在同一个 delta 里的先后换一下，输出就变了——也就是说，一旦并行让这个
顺序变成"不确定"，依赖它的程序就不再稳定。

### 2.4 类型系统（与共享格有关的部分）

- 类被分成值类型和引用类型（`SemanticClassifyValueTypes.penguin`）。自动判定要求**所有
  字段都是值样的**（递归检查，包含枚举的负载和泛型参数）；但显式写了 `impl IValueType`
  的类直接算值类型，**不检查字段**（`:197-217`）——它可以带引用字段。
- 值拷贝是**整块复制**（按字节 `memcpy`）：绑定、传参、取字段三处都复制
  （`LLVMEmitter.penguin:3693-3714`、`:1424-1443`、`:4141-4160`）。复制是**浅的**：值类里
  的引用字段（比如 `string`）复制的是指针，两份副本共享所指对象。`mut` 只是编译期的修改
  权限，不影响内存布局。
- **一个显式 `mut` 字段能穿过不可变绑定漏出可变别名**：不可变绑定的对象，其显式声明为
  `mut` 的字段读出来仍是可变的（`SemanticBindExpressions.penguin:3707`）。这决定了全局变
  量的分类必须看**类型的深可变性**，不能看绑定有没有 `mut`（4.3 节）。
- `string` 在分类层被当作 primitive 值类型（`:355-356`），在 LLVM 输出层是垃圾回收堆上的
  指针。字符串字面量是编译期常量，不进堆；运行期的字符串操作（拼接、子串、转字符串、读
  文件）都分配新对象，没有任何原地修改（`std/c/core_builtin.c` 的字符串函数全部返回新对象）。
- 函数值（闭包）恒为引用类型（`:184-190`）；接口类型的值经过装箱成为堆引用；没有实现
  `IReferenceType` 的接口大小未知，只能作为局部变量或参数。
- 原生路径（EmperorPenguin → LLVM → C 运行时）**没有任何原子操作**：`AtomicI64` 只存在于
  BabyPenguin 的 C# 虚拟机里。

### 2.5 垃圾回收现状

green tea 回收器（`std/c/gc.c`、`gc_span.c`）：

- 保守扫描 + 精确根混合：根集合 = 运行中协程的帧链、每个停靠协程保存的帧链、每个协程的
  栈扫描区、全局变量根、元编程钉住的对象、新对象隔离环，外加主栈的一段保守覆盖。
- 堆是全局单一段堆（span heap），按大小类别管理槽位，位图清扫；对象**从不移动**。
- 全部状态是单线程静态变量，**没有任何锁和原子操作**；写屏障函数存在但是空的
  （`gc.c:1989-1995`，注释说明没有记忆集）。
- 回收只在安全点发生：分配线程不内联回收，而是在 Penguin 代码的安全点检查（`gc.c:543-546`、
  `:2076-2096`）。

### 2.6 通道族现状

`Fifo`、`LatestChannel`、`MergeChannel`、扇出、扇入、`Event` 都是普通 Penguin 类，内部没有
任何同步机制，靠"单线程 + 不会被打断"成立。背压的写法就是循环让出：

```
// Fifo.write（scheduler.penguin:836-843）
while (self.is_full()) { wait; self.check_closed(); }
self.deliver(v);
```

三个细节对后面几章重要：

- **`Event.emit` 末尾自带一个让出**（`:1549`），所以广播的"效果"落在下一个 delta——事件类
  测试因此天然对 delta 内顺序不敏感。计划中的运行时把这个"蹭一个让出换来的延迟"改成显式
  的延迟投递（8.3 节）。
- **`LatestChannel` 会把同一个 delta 的多次写入坍缩成最后一个值**（`push`，`:950-970`）。
  "最后一个"是 delta 内顺序的函数，所以同 delta 多写者时这个值是未规定的。
- **背压用裸 `wait` 轮询**。在"就绪即恢复"的粒度下，这个写法必须改成真正的条件等待，否则
  每次补货都要多花一个 delta（6.2 节）。

## 3. 线程模型：放置自动，"不搬家"

### 3.1 域（domain）

一个**域**指"一个 OS 线程以及它上面跑的所有东西"。放置规则：

- 协程默认属于**创建它的线程**（亲和性）。
- 标记为**可偷**的协程，在被第一次执行之前，可以被任何空闲线程领走执行。
- 持有不可共享引用的协程不可偷。

### 3.2 决定 A：已启动的协程永不换线程

**一个协程从它第一次运行那一刻起，就固定在那条线程上，直到结束。** "可偷"只描述还没跑过
的新协程：它出生时排在创建者的队列里，其他空闲线程可以把它领走，第一次运行在哪个线程，
它就在哪个线程过完一生。

这条决定带来四件事：

1. **不需要分析"停顿时手里攥着什么"。** 协程的栈不会离开它的线程，所以栈上的局部变量（包
   括从别处拿到的引用）永远只被这条线程访问。反过来说，如果允许把停靠的协程搬到别的线程
   继续跑，就必须在每次让出时检查"此刻栈上活着的值哪些不可共享"，否则会出现下面这种竞争：

   ```
   class Cell { v: mut i64; }            // 引用类型，没有锁 ⇒ 不可共享

   async fun worker(c: Cell) { c.v = c.v + 1; }   // 参数不可共享 ⇒ 这个协程固定

   // 在另一个"可偷"的协程里：
   let c = new Cell(0);
   let f = async worker(c);     // 子协程固定在本线程，并继续使用 c
   wait f;
   c.v = 99;                    // 父协程也还在用 c
   ```

   如果父协程能被搬到别的线程，它和固定在原线程的子协程就同时访问同一个 `c`。禁止搬家
   之后，这段代码天然正确：父子都在同一条线程上，串行执行。

2. **每个线程的本地堆只需要自己管。** 不会出现"对象分配在线程甲，而持有它的人跑到了线程
   乙"这种情况，所以不需要按执行上下文决定"这次分配该进哪个堆"（第 10 章）。

3. **固定协程的创建，父子必然同线程。** 固定的子协程跑在创建者当前所在的线程上，而创建者
   不会搬家，所以固定的父子总是在同一条线程——现在这套不加锁的结果容器可以直接用。只有
   **可偷的**创建才需要加锁版本的容器（见 4.7 节）。

4. **唤醒必须送回属主线程。** 一个停靠的协程只能在自己的线程上继续跑，所以别的线程想叫醒
   它，必须把"可以继续了"放进**那条线程的队列**。工程后果：线程不能无限期睡在 I/O 等待
   上，必须有唤醒通道（`eventfd`、self-pipe、`WaitOnAddress` 之类），详见第 12 章。

代价有两笔，必须接受：

- **delta 边界不能再重新分配工作。** 每个收敛点上"就该轮到"的协程全都是已经跑过的，一个
  也搬不动，它们各自回到出生线程；**并行度只来自新协程的首次放置**。对"开局一次性创建一批
  进程、之后每个 tick 都醒来干活"的仿真模型，这等于开局做一次静态划分（划分本身仍然可以
  并行，但之后不再调整）；对"每个任务创建一个协程"的模型（请求式服务），每次创建都是一次
  放置，负载均衡效果好。某个协程突然变重时，没有补救手段。
- **谁和谁同线程是逐次运行可变的**（哪个线程先领走哪个新协程是运行期竞争）。这个不确定性
  用户无法通过写法消除，但在"只用延迟提交构件交流"的程序里它不可观测（第 6 章）。

### 3.3 一个 delta tick 的结束条件

一个 delta tick 结束的条件是**全局再没有任何可运行的工作**（见 0.2 节），不是"每条线程都
跑到了碰头点"。原因：新创建的协程本 delta 就能跑；如果有线程提前收工而队列里还有它没领走
的活，这个协程就会滑到下一个 delta，"创建后本 delta 就能跑"这条性质（很多现有测试依赖
它）就没了。

在并行形态下，"全局再没有任何可运行的工作"是一个需要跨线程确认的条件，而且必须处理一个
经典竞态：一条线程决定"我先收工"之前要再检查一次，否则会漏掉刚刚投递进来的活（第 12 章）。

## 4. 什么数据可以跨线程（共享格）

### 4.1 四个谓词

以下谓词都能由编译器从类型计算出来（计划的 Pass 10）：

| 谓词 | 含义（大白话） | 例子 |
|---|---|---|
| `Sync(T)` | T 自带锁，方法可以随便被多个线程同时调用 | `AtomicI64`、`Mutex`，以及自带锁的通道 |
| `Imm(T)` | T 深不可变：创建之后内容不会变（递归所有字段，含显式 `mut` 字段检查），所以多个线程只读是安全的 | `i64` 等基本类型、`string`、全部字段不可变的类 |
| `ValueShare(T)` | T 是值类型，并且**它的所有字段（递归）都可共享** | 只含 `i64`/`string` 字段的值类 |
| `Own(T)` | T 是 `Ownership<U>`，独占所有权已经验证过 | 第 9 章 |

```
Shareable(T) = Sync(T) ∨ Imm(T) ∨ ValueShare(T) ∨ Own(T)
```

两类用法要分清：

- **按引用共享**（两个线程同时持有同一个对象）安全，当且仅当 `Sync ∨ Imm`。
- **零拷贝迁移**（对象的引用从一条线程交给另一条线程）安全，当且仅当 `Shareable`。

其余类型——接口装箱值、函数值、带不可共享字段的裸值类型——不可共享。持有它们的协程被
**固定**。固定不是错误，是保守回退：编译器用 `-Wconcurrency` 给出原因链，例如"参数 1
`List<T>` 不可共享""触摸了全局 `x`"。

### 4.2 两条必须自己算的特例

- **不能直接复用现有的"是不是值类型"判定。** 显式 `impl IValueType` 的类不检查字段
  （2.4 节），所以它可以带引用字段。下面这个类的实例会被整块复制，但复制出来的是共享同一
  个列表的指针：

  ```
  class Holder { l: mut List<i64>; impl IValueType; }   // 值类，但字段是引用
  ```

  这种实例如果随协程栈跨线程，两个线程就会同时改同一个列表。所以 `ValueShare` 必须自己
  递归遍历字段，环（自引用类型）按"未证明即不可共享"处理。

- **`string` 安全靠的是不可变，不是"它是值类型"。** 字符串在运行期是堆指针；它安全的唯一
  理由是**没有任何操作会原地修改它**。

### 4.3 全局变量：按类型的深可变性分类

全局变量的分类看**类型**（递归到每个字段有没有显式 `mut`），不看绑定的 mutability——因为
显式 `mut` 字段能穿过不可变绑定漏出可变别名（2.4 节）。三类：

- **深不可变类型**（`Imm(T)`，递归无 `mut` 字段）：任意线程读。
- **`Sync` 类型**：任意线程用。
- **其余一切**（`mut` 绑定，**以及**非 `mut` 绑定但类型内部可变——比如 `let config :
  Settings = ...` 而 `Settings` 含显式 `mut` 字段）：**所有权封闭**——属于初始化它的域
  （主线程），任何可能碰到它的协程都被固定到该域。

第三类必须发一条 **info 诊断**（这类全局是并行度的隐性杀手，用户应当被告知）：

```
info: global 'config' has interior mutability (field 'v' is 'mut');
      it will be confined to one domain and every coroutine touching it
      will be pinned — forcing a mutable field here lowers multi-thread
      parallelism; make the type deeply immutable or use a Sync container
```

为什么不能把全局变量静态分组、每组分配给一条线程：**偷取是运行期事件**（哪些线程会跑哪些
协程在编译期不可知），而且**两个全局变量可以在运行时指向同一张对象图**（别名），静态别名
分析不可判定。按变量表分组会把一张对象图劈给两条线程。

"每组可以去不同线程"这个意图留给后续的**组迁移**扩展（一组对象静止时整体过户到另一条线程，
连同它的固定协程一起搬），第一版不做。

### 4.4 函数的副作用（effects）

对每个函数保守累积（按可达调用闭包）：

```
Effects(f) = 可达的全部全局读写
           ∪ 可达的 extern（C 函数）调用集合
           ∪ {unknown_virtual}   接口虚调用取所有已知实现的并集；跨动态库视为未知
           ∪ {meta_call}         元编程调用，第一阶段一律视为未知
```

`extern` 需要白名单（纯函数、C11 原子、线程安全 I/O）；不在白名单里的 extern 会让协程固定。

### 4.5 可偷判定

```
Stealable(async f(args)) ⇔
    每个参数类型 Shareable          （上下文字段本来就是一整份拷贝）
  ∧ 返回类型 R Shareable            （结果容器要跨线程交付）
  ∧ Effects(f) 触摸的全局全部为 Imm 或 Sync
  ∧ 可达 extern 全部在白名单内
  ∧ 没有 unknown_virtual，没有 meta_call
```

不满足就固定，不报错。返回类型出现在判定里，是因为结果容器本身跨线程（见 4.7 节）。

### 4.6 四条不变式

- **INV1（封闭）**：任何非 Sync 对象的可变访问，只发生在它出生域的单个线程执行流里。
- **INV2（跨线程流）**：线程之间传递引用，只通过 Sync 对象内部（它收发的值必须可共享）或
  不可变对象。
- **INV3（全局）**：封闭类全局（4.3 节第三类）只在属主域被访问；`Imm` 全局任意读；`Sync`
  全局任意用。
- **INV4（回收）**：堆全局共享且不移动；标记在所有线程都停下的安全点进行。

归纳论证（骨架）：初始时单线程跑初始化代码，四条平凡成立。此后每一步：

1. **本地执行**：持有不可共享引用的协程固定，永远在出生线程；它创建的固定子协程同线程；
   可偷的子协程只携带可共享的参数（INV1、INV2）。
2. **领走新协程**：只可能领走可偷的，它携带的状态全部可共享；它可达的全局全部是 Imm 或
   Sync（INV3）。
3. **跨线程消息**：通道本身是 Sync，元素可共享（编译期强制）。
4. **分配**：新对象属于当前线程的域。
5. **回收**：所有线程停在 delta 边界或安全点后枚举全部根；堆不移动，跨线程指针永不失效
   （INV4）。

于是：非 Sync 对象的可变访问被限制在单线程执行流里（无数据竞争），不移动的堆保证指针不会
失效（无内存错误）。

### 4.7 创建/等待协议自己会跨线程

`async f(args)` 生成的结果容器会被父协程轮询、被子协程写入。既然父协程是自己读一次容器、
子协程写一次容器，那么：

- **固定**的子协程：父子同线程（决定 A 的直接结果），现在的普通容器就够用；
- **可偷**的子协程：父子可能在不同线程，容器必须自带同步（完成标志用原子 + 结果的可见性
  由"先写结果、后置标志"的次序保证），而且**返回类型必须可共享**。

由此得到一条规则：**结果容器是否加锁，取决于这个创建点是否可偷**——这是编译期常量，落在
生成代码里即可。

顺带说明：`wait f` 不再需要"每个 delta 让出一次再问一遍"的轮询（2.1 节），它应该变成**条件
等待**：子协程完成时唤醒父协程，父协程在当前 delta 内就接着跑（8.3 节）。这不影响正确性，
只影响时间结构。

## 5. 六个容易搞错的地方

这一节列的都是"看起来没问题、实际有反例"的设计点。实现时每一条都要有对应的检查。

### 5.1 只看创建时传进去的变量不够

```
async fun worker() { let l = get_list(); l.push(1); }
```

这个协程零参数，但它通过 `get_list()` 拿到了全局列表的引用。判断能不能偷必须覆盖协程体的
**全部可达调用闭包**（4.4、4.5 节的 effects），创建点的输入只是其中一项。

### 5.2 值类型的判定必须递归查字段

见 4.2 节的 `Holder`。如果直接复用"是不是值类型"，`Holder` 会被判成值类型，其实例随栈跨
线程时携带的是共享指针。

### 5.3 `string` 靠的是不可变，不是"它是值类型"

如果按字面规则把它当值随栈带走，堆指针确实会跨线程——这碰巧安全，但安全的依据必须是
`Imm` 显式入格，并且要有"所有字符串操作都产生新对象"这条审计结论支撑（2.4 节已确认）。

### 5.4 全局变量不能静态分组到线程

见 4.3 节：偷取是运行期事件，运行时别名让"分组单位"必须是对象图而不是变量。

### 5.5 创建/等待协议自己产生跨线程引用

见 4.7 节。这条规则（返回类型也必须可共享）不是额外限制，是容器跨线程的直接结果。

### 5.6 阻塞原语必须变成让出点，回收必须有安全暂停点

1. **同步原语的阻塞不能阻塞线程本身。** 如果 `Mutex.lock()`（计划的 API）用操作系统原语把
   线程睡住，会与固定协程组合出死锁：同一个线程上，持锁的协程可能永远排不到。所以同步类
   型的阻塞操作必须**让出协程**，让线程去跑队列里的其它活。在"就绪即恢复"的粒度下，这把锁
   的等待者可以在同一个 delta 内被唤醒，代价是锁的实现要用"停靠 + 唤醒"而不是自旋。
2. **回收需要安全暂停点。** 只算数、不分配、不让出的协程会让"全世界停下来"停不下来；而它
   同时在改对象图就会让标记漏边，回收掉还活着的对象。这不是"延迟变长"的问题，是正确性
   问题。在有 delta 结构的形态下，delta 边界本身就是安全暂停点（第 7 章），所以不需要在
   循环回边插检查；只有自由形态（无 delta）才需要。

## 6. 确定性：能给什么、不能给什么

### 6.1 结论

| 使用方式 | 确定性 |
|---|---|
| 只读的不可变数据；只在一个协程里用的容器 | 值和时间位置都确定 |
| 多个协程在同一个 delta 里读写同一个**立即可见**的对象（今天的 `Fifo`、`LatestChannel`）：多写者时"合并出哪个值"没有依据 | **值不保证**；如果程序再根据这些值决定分支、或者决定要不要推进 delta/tick，那么**时间位置也不保证** |
| 多协程共享的数据全部放在**延迟提交**构件里（`Signal<T>`、延迟通道、`Event`），且**每个通道只有一个等待者** | 值和时间位置都确定（合并规则显式给定；多等待者的配对见 6.9 节） |

一句话：**语言不承诺全局确定性；语言提供"确定性子集"所需的构件和检查工具。**

### 6.2 不确定的两个来源

**(一) 值。** 同一个 delta 里两个协程写同一个立即可见的对象，"最后是多少"没有语义依据：

- `LatestChannel` 会把同一个 delta 的多次写入坍缩成一个值（2.6 节），谁是"最后"未规定；
- 容量 1 的通道上两个写者同时写，谁写进去、谁停靠，未规定。

**(二) 由值派生的时间位置。** 如果程序根据上面这些值决定"走哪条分支"、或者决定"要不要推进
delta"（`wait;` / `wait n;` 出现在条件分支里），那么"某件事发生在（第几个 tick，第几个
delta）"也跟着不确定。把"等条件"写成 `while (!cond) wait -1;` 的自旋，或者写成
`while (!cond) wait;` 的"每个 delta 重试一次"，都会让时间停住（0.3 节），后者还会让"哪个
delta 在重试"取决于谁先跑。

反过来有一条好消息：**只把等待写成条件等待（通道/事件/信号）、并且不根据竞态出来的值决定
要不要推进 delta 的程序，同一个 delta 内的先后只影响值，不影响时间位置。**

下面这个实测例子说明"顺序敏感"有多容易发生：只有一个写者、一个读者，把两个 `initial`
块换个位置（只改变同一个 delta 内的先后），输出就变了。要紧的是：**这个程序在新语义下依
然是顺序敏感的**——因为它的读者用的是"试取 + 失败就 `wait;`"（轮询），不是条件等待。把
读者的循环换成 `let v : i64 = wait ch;`（条件等待）之后，两种顺序的输出才会一致（写者投递
即唤醒读者，全部发生在同一个 delta 里）。这正是"用对构件"的实证：

```penguin
class Cnt { v: mut i64 = 0; }

let ch : mut __builtin.Fifo<i64> =
    new __builtin.Fifo<i64>(1, new __builtin.FifoPolicy.backpressure());
let taken : mut Cnt = new Cnt();      // 已经取走的个数
let delta_no : mut Cnt = new Cnt();   // 每个 delta 加一（把 delta 编号打印出来）

initial {                             // W：唯一的写者
    let i : mut i64 = 1;
    while (i <= 3) {
        ch.write(i);
        println("W wrote " + cast<string>(i) + " @" + cast<string>(delta_no.v));
        i += 1;
    }
    println("W done @" + cast<string>(delta_no.v));
}

initial {                             // C：唯一的读者，试取 + 失败就推进一个 delta
    while (taken.v < 3) {
        let v : Option<i64> = ch.try_poll();
        if (v.is_some()) {
            taken.v += 1;
            println("C got " + cast<string>(v.some) + " @" + cast<string>(delta_no.v));
        } else {
            wait;
        }
    }
    println("C done @" + cast<string>(delta_no.v));
}

initial {                             // M：观察者，每个 delta 把编号加一
    while (taken.v < 3) { delta_no.v += 1; wait; }
}
```

```
顺序 [W, C, M]                    顺序 [C, W, M]
W wrote 1 @0                     W wrote 1 @0
C got 1 @0                       C got 1 @1
W wrote 2 @1                     W wrote 2 @1
C got 2 @1                       C got 2 @2
W wrote 3 @2                     W wrote 3 @2
W done @2                        W done @2
C got 3 @2                       C got 3 @3
C done @2                        C done @3
```

整条流水线的相位差了一个 delta。读者先跑（顺序 [C, W, M]）时，它在写者投递**之前**试取、
扑空、停靠到下一个 delta，于是所有后续事件都晚了一个 delta；换成条件等待就没有这个窗口。

### 6.3 三条"看起来能救、其实救不了"的思路

**（一）"只要不写多个写者就行"——不够。** 多写者只是"值不确定"的一部分；只要跨协程共享的
东西是立即可见的容器，程序就可能与线程数有关（6.2 节的第二类来源）。

**（二）"规定同 delta 多写者按时间先后"——不行。** 并行状态下"谁先谁后"是运行期事实，不是
可以规定的语义；用一个不确定的东西去规定另一个不确定的东西没有意义。要确定，只能按**写者
的身份**定：端口号、创建序号这类在编译期就固定下来的东西（见 6.5 节）。

**（三）"至少同一线程内是确定的"——不够。** 谁和谁在同一条线程上是逐次运行可变的（3.2 节），
所以"同一线程内确定"给不出任何可依赖的承诺。

### 6.4 延迟提交：让"本 delta 的动作"与顺序无关

**延迟提交**（deferred commit）的规则只有两条：

1. 写进去的值**不立刻生效**，先挂在旁边；
2. 读到的值永远是**上一次 delta 边界提交的那个值**。

提交发生在 **delta 边界**（0.2 节收敛点的第 1 步）。这样"本 delta 都发生了什么"就与协程的
先后无关：这个 delta 的状态变化只取决于"delta 开始时是什么样"加上"这个 delta 有哪些写入"，
与写入的先后无关。于是 6.2 节的问题消失了，时间位置与线程数无关。

由此也得到一条好记的规则：

> **延迟是构件的属性，不是调度机制的属性。**
> 想要"每传递一次消耗一个 delta"的延迟，就用延迟构件（`Signal`、延迟通道、`Event`）；
> 用普通容器就是在同一个 delta 内零延迟地互相看见，代价是顺序不规定。

同一个意图的两种写法：

```penguin
// 写法一（今天）：立即可见的容器。两个协程在同一个 delta 里读写它，
//   谁先谁后决定后面的时间位置，所以结果与线程数有关。

// 写法二（计划）：延迟提交的构件。写进去下一个 delta 才可见，读到的永远
//   是上一次提交的值，本 delta 谁先谁后不影响任何结果。
let s : mut Signal<i64> = new Signal<i64>(0);   // 单写者信号
```

现在语言里已经有一个这样的构件：**`Event`**。它的 `emit` 末尾带一个让出（2.6 节），所以广播
的效果落在下一个 delta，事件类程序天然与 delta 内顺序无关。计划中把它改成显式的延迟投递
（在 delta 边界提交），语义不变。

### 6.5 多个写者时，值由"谁写的"决定

延迟提交解决了"谁先谁后"，但没解决"两个人写同一个东西，最后是多少"。这必须显式定：

- 一个**只有一个写者**的信号/线：天然确定。
- 有多个写者的信号/线：必须选一条**按身份**的规则，比如"端口号小的赢""按端口号依次覆盖"
  "调用用户给的分辨函数"。按时间先后（"最后一个写的赢"）在并行下等于未规定。

这也是硬件里的做法：多个驱动器接同一根线时，靠端口优先级或分辨函数决定电平。

### 6.6 为什么延迟提交不能做成"给普通字段加个修饰符"

给类的普通字段（比如一个 `i32`）单独加"延迟提交"，有三重麻烦：

1. **值类型会被整块复制**（2.4 节）。如果字段里带着"还没提交的写"，每次拷贝都会把这份挂起
   状态一起复制，副本之间的挂起写是什么关系、提交时落到哪个副本上，都没有自洽答案。
2. **内存与回收成本**。每个延迟字段都要多一份影子槽和一个"本 delta 写过"的标志，实例变大；
   而对象布局是垃圾回收扫描的依据（字段偏移表和"哪些字段是指针"的表），影子槽必须一并进
   这两张表，扫描也跟着变贵。
3. **读到的可能是旧值**，这个语义必须让用户看得见——藏在字段修饰符里会变成难查的 bug。

所以延迟提交只能是**单独的类型**（一个堆对象，内部是"当前值 + 待提交值"），不能是字段属性。
实现上可以很省：单写者、整值写入时，用两个槽按 delta 的奇偶交替，提交就是切换一次索引，
不需要额外标志位、不需要拷贝。

### 6.7 两个形态的关系：自由形态就是"时钟不前进的并行仿真形态"

计划里有三个形态（详见 7.3 节）：单线程的 sim（今天）、delta 内并行的 sim-mt、没有 delta
结构的自由形态 free-mt。在"tick / delta tick"这个定义下，sim 与 sim-mt 的区别只是"一个
delta 用几条线程跑"，而 sim-mt 与 free-mt 的区别只剩一件事：

> **在 delta 边界上要不要推进虚拟时钟。** sim-mt 要（定时器、`wait n;` 靠它）；free-mt 不要
> （时间交给真实墙钟，没有 tick）。

所以：**对不使用仿真时间（没有 `wait n;`、没有定时器）的程序，free-mt 与 sim-mt 的行为
一致**——delta 边界除了"提交延迟写"和"判断是否结束"之外无事可做。这也回答了一个自然的
问题："能不能把两者当成一套东西实现"：实现上可以共用同一套内核（工作窃取、收敛判定、
唤醒、封闭分析），语义上要按"用不用仿真时间"分开陈述。

一处待定：延迟提交在 free-mt 里的提交点。free-mt 的 delta 边界没有"推进时间"的含义，如果
把提交点定义为"系统空闲"，那么在一个持续繁忙的服务里写入可能长时间不可见。两种处理：在
free-mt 里禁用延迟构件（只用"立即 + 加锁"的容器），或者接受"提交点在空闲时刻发生"并把
这条写进文档。

### 6.8 工具：把"用户用对构件"变成可检查的事

确定性从语言承诺降级成程序性质之后，必须给出可判定、可检查的手段，否则用户无从下手：

1. **编译期诊断（计划）**。Pass 10 已经有"哪些对象被哪些协程可达"的数据，可以据此给出：
   - "本程序有 3 个可偷的创建点，会并行执行；delta 内的顺序与时间位置不保证"；
   - "对象 `x` 被多个协程可达，但它不是延迟提交构件，也不是只读"（指向 `Signal<T>`）；
   - "多写者的信号 `s` 没有指定合并规则"；
   - 4.3 节的内部可变全局 info。
2. **运行期检测器（计划）**：`--shuffle-deltas=SEED`。在单线程形态下按种子打乱每一个
   delta 内的恢复顺序，同一个程序用多个种子各跑一次，比较输出。**输出不一致就说明这个
   程序依赖了 delta 内的顺序**。这是"我们不再保证确定性"的配套工具：不承诺，但帮你查
   出来。

### 6.9 仍然不确定的东西

即使把共享数据全部搬进延迟构件，下面这些仍然不确定：

- **多写者的值**（没有指定合并规则时，见 6.5 节）。
- **多等待者的配对**：两个消费者同时停靠在同一个通道上时，谁拿到哪一个值由调度决定（提交
  顺序是确定的，配对不是）。需要逐个消费的场景要么保证单等待者，要么给通道指定按等待者
  身份的定序（开放问题，14 节）。
- **两个协程在同一个 delta 里访问同一个裸可变引用对象**（比如共享一个 `List`）。这类对象
  没法做成延迟字段（6.6 节），只能靠纪律（编译器诊断 + 检测器）约束。
- **跨协程的输出行序**：同一个 delta 里两个协程各自 `println`，两行的先后不规定。测试要用
  行集合比较或显式同步点，不能逐字节比较。
- **delta 永不收敛**：同一个 delta 永远收敛不了的情况——两个协程互相唤醒（例如通过立即可见
  通道来回写），或者某个协程在 `while (!cond) wait -1;` 里自旋（0.3 节）。这类程序连一个
  delta 都过不去。计划中为它加一个明确的诊断（第 12 章），而不是无声挂起。
- **时间被钉住**：另一种停顿——delta 在不停收敛（每个 delta 都有协程登记"再来一个"），但
  虚拟时钟永远不前进，于是所有"等时间"的协程都醒不过来（0.3 节的 `while (!cond) wait;`
  就是这种）。今天实现里裸 `wait;` 不给 tick 设卡，这个洞被掩盖着；统一之后它对用户是可见
  的，因此需要诊断（第 12 章）。

## 7. 并行形态与 delta

### 7.1 语言契约：delta 内跨协程读写不可靠

**同一个 delta tick 内，跨协程的读写只保证"无数据竞争"，不保证读到什么**；只有 delta 边界
（含仿真时间推进）之后，读到的才是已提交状态，才可靠。等待点（`wait ch` / `wait ev` /
`wait f` / 推进 delta / 时间前进）都是可靠的边界。这是这类语言一贯的立场：同一个 delta 内
的求值顺序不加规定。

### 7.2 sim-mt：delta 内并行 + delta 边界收口

- **delta 内**：任何就绪的协程立刻（在某条线程上）接着跑，谁先谁后不规定；一个协程一个
  delta 里可以跑多次；新创建的协程本 delta 就能跑（跟创建者在同一条线程，除非它是可偷的、
  被别的线程领走）。delta 内没有碰头点。
- **delta 边界**：等全局再没有任何可运行的活（3.3 节），然后**单线程**执行 0.2 节列的七步。

逐项核对现有机制（"现有"指今天单线程实现的那些机制）：

| 现有机制 | 并行形态下怎么处理 | 是否保持 |
|---|---|---|
| "让出 = 排到下一个 delta" | 保留为 `wait;`（= `wait 0;`）的含义；另加"只让出执行权"的负数写法（`wait -1;`），它被调度器立刻重新调度 | 行为变化：依赖"让出一整个 delta"的用例要改（第 13 章）；负数写法是新增能力 |
| delta 内先进先出顺序 | 变为不规定（契约允许） | 语义合法；依赖它的测试要重写（第 13 章） |
| 统一虚拟时钟 | 只在 delta 边界写，delta 内只读（边界是内存屏障，保证可见） | 是 |
| 时钟推进决策 | 边界七步的第 5 步 | 是 |
| "本 delta 有没有活动"的门控 | **退役**：新定义下"还有可运行的活"就是这个判据的精确版本 | 简化 |
| 定时器注册 | delta 内进各线程暂存，边界按（截止点，创建序号）确定性归并 | 是 |
| 外部输入等待 | 边界七步的第 4 步（每次边界都非阻塞探测）与第 6 步（只剩 fd 等待者才阻塞） | 是 |
| 静止指纹（判退出） | **退役**：退出只看"所有协程是否都结束了"（7.4 节） | 简化 |
| 背压用裸 `wait` 轮询 | 改成条件等待（消费方一取走就恢复生产者） | 必须改，否则每次补货多花一个 delta（6.2 节） |
| `Event.emit` 末尾的裸让出 | 改成显式的延迟投递（边界提交） | 语义不变 |
| `wait f` 的轮询 | 改成条件等待（子协程完成时唤醒父协程） | 语义不变，延迟变小 |
| 垃圾回收 | delta 边界本身就是"全世界停下"的安全点 | 是（第 10 章） |
| 不让出、不分配的死循环 | 与今天一致（挂起，没有回归）；另加"delta 永不收敛"诊断 | 是 |
| 并行度来源 | 只有新协程的首次放置（决定 A 的代价） | — |

性能特征：一个 delta 可以很长（一路跑到底），**碰头只在 delta 边界发生**。所以"每传递一次
就碰头"的开销没有了——细粒度流水线只要用立即可见容器，整条流水线可以在同一个 delta 内跑
完；用延迟构件时，每传递一次正好消耗一个 delta（这正是硬件里"每级寄存器一拍"的模型）。

### 7.3 三形态

| | sim（默认，现状） | sim-mt（新） | free-mt（后期） |
|---|---|---|---|
| 线程 | 1 | N（delta 内并行 + 边界收口） | N（无 delta 结构） |
| 时间 | tick + delta | tick + delta（不变） | 真实墙钟；`wait;` 退化为让出 |
| 一个 delta 的含义 | 一次完全收敛（实现上目前是"扫一遍就换"） | 一次完全收敛 | 没有 delta |
| 确定性 | 全确定（实现决定顺序） | 跨 delta 确定（对只用延迟构件且单等待者的程序） | 只保证无数据竞争 |
| 通道/事件 | 现实现 | 延迟构件（第 8 章） | 立即 + 加锁的构件 |
| 回收安全点 | 不需要（单线程） | delta 边界 | 循环回边检查 |
| 用途 | 硬件建模、逐字节测试、语言服务器、自举 | 用户程序的保守并行 | 高吞吐服务的激进并行 |

同一份源码、同一套封闭分析与同步构件。**编译器自己永远以 sim 形态编译**（自举的 md5
收敛不受影响；自举走 `--disable-coroutine`，根本不进调度器）。

### 7.4 退出与挂起

只有一种情况会自动退出：**所有协程都结束了**。除此之外：

- 还有协程在等外部输入（文件描述符）→ 阻塞在 `poll` 上等外部事件（这是服务型程序的正常
  长期状态）。
- 还有协程停靠着、但没有任何外部事件源、也没有定时器 → **静静挂着**：不报错、不退出、不
  打印任何东西。将来可以加调试用的检测（比如打印"还有 N 个协程在等，它们分别停在什么
  条件上"），但语言不承诺检测死锁。

这条规则是选择的结果：区分"正常等待"和"卡住"需要猜测用户意图（今天的实现用"状态两个
delta 不变"来猜，代价是会把"永远等待的接收者"当成正常结束），而猜错的代价比"多等一会儿"
更大。所以第一版选择简单的那条：**只要还有协程活着，程序就活着**。

对现有测试的影响很直接：任何"某协程永远等着、其他协程跑完就退出"的用例，在这条规则下会
挂起，必须改写成显式结束（例如打印完之后调用退出，或让等待的协程也有终止条件）。实测需要
改写的用例见 13.2 节。

## 8. 通道族与同步构件

### 8.1 分档原则

> **跨协程共享的可变数据用延迟提交构件；只在一个协程内用的数据用普通容器。**

- 跨协程：`Fifo`（延迟版）、`Signal<T>`、`Event`、线语义的连线。
- 协程内：`Queue<T>`、`List<T>` 等普通容器，立即生效，随便用。

编译器可以诊断违反（6.8 节第 1 条）：一个普通容器被多个协程可达，就是确定性隐患。`Fifo`
默认实现为延迟提交（它的用途就是跨协程通信），`Queue` 保持立即（它的用途是协程内的数据
结构）。

### 8.2 构件清单

| 构件 | 语义 | 状态 |
|---|---|---|
| `Queue<T>`、`List<T>` | 立即生效的普通容器，只在协程内用 | 已有 |
| `Fifo<T>` | 跨协程通道；**改成延迟提交**，容量按 delta 起始状态判定 | 已有（当前是立即） |
| `Signal<T>` | 单写者的信号：写挂起、读旧值、delta 边界提交 | 计划 |
| `Event<T>` | 广播；`emit` 的效果落在下一个 delta | 已有（已经是延迟，实现方式待改） |
| 线语义通道（`LatestChannel`） | 端口/连线；延迟提交 + 多写者按身份合并 | 已有（当前是立即） |
| `AsyncQueue<T>` | 立即生效 + 加锁的队列，供自由形态的服务类程序使用 | 计划 |
| `AtomicI64`/`AtomicBool`、`Mutex`、条件等待 | 基础同步原语 | 计划 |

（等任意布尔条件的 `wait cond` / `wait change(x)` 不在此列——它们没有唤醒源，作为语法删除，
见 0.3 节；等状态用上表的构件表达。）

### 8.3 延迟通道要钉死的四件事

1. **写挂起、读已提交**（6.4 节），提交点在 delta 边界。延迟是**构件的属性**：用立即可见
   容器就是同一个 delta 内零延迟互相看见（顺序不规定），要"每传递一次消耗一个 delta"就用
   延迟构件。
2. **容量与背压**：容量判断只看已提交状态（否则又回到顺序依赖）；同一个 delta 里多个写者
   可能超出容量，边界按**写者身份**依次放行，落选者停在"通道不满"的条件等待上（消费方一
   取走已提交的值就唤醒它们，等价于一个按端口号仲裁的总线）。背压必须实现成**条件等待**，
   不能用裸 `wait` 轮询。
3. **关闭（`close`）**：关闭也要在提交阶段按同一条身份顺序落地，否则"关闭瞬间生产者还能不能
   写"又是顺序依赖的。
4. **调用方的延迟**：`wait ch` / `wait f` / `wait ev` 都实现成"条件满足即在当前 delta 内恢
   复"，不要保留今天"每个 delta 问一次"的轮询（那会让每次通信凭空多花一个 delta）。

### 8.4 条件同步：元素可共享才加锁

通道族按元素类型条件性地实现同步接口：元素类型可共享时，注入"带锁 + 让出式背压"的实现；
元素不可共享时，**不实现**同步接口——于是这个通道类型本身就不可共享，不能经任何跨线程的
途径传递，只能留在同一个域里，两端自动同域。

判定与实现必须同源生成（同一份判据既决定"虚表里有没有锁"，也决定"分析结论是不是可共享"），
否则会出现"分析认为它安全、而实现里没有锁"。泛型接口（`ISink<T>` 之类）的可共享性随参数走。

有一个细节：实现同步的阻塞方法必须**让出协程**而不是阻塞线程（5.6 节），互斥锁内部因此要带
一个停靠队列；在"就绪即恢复"的粒度下，唤醒在同一个 delta 内生效。

### 8.5 静默固定需要可见性

传引用的通道会把整条流水线固定成单线程：程序正确，但慢，而且用户没有任何提示。所以
`-Wconcurrency` 要给出提示："元素类型不可共享，这些协程被固定在同一个域里；要跨线程请改用
`Ownership` 或换可共享的元素类型。" 同样的诊断也适用于"没有任何可偷创建点，本程序不会并
行"。

## 9. 显式转移：`Ownership<T>`

### 9.1 原则

> **放置自动推断（错了只损失并行度）；转移显式声明（错了才是数据竞争）。**

### 9.2 三条规则

```
enum Ownership<T> { owned: T; not_owned; }

fun owned(v) -> Ownership<T>      // 构造：编译期验证独占
fun move(mut this) -> T           // 取出：把自身置为 not_owned
```

1. **构造检查（编译期，函数内可判定）**：`Ownership.owned(v)` 要求 `v` **新鲜**——它引用的
   整张对象图都是这次新建的（或深不可变的）。新鲜性按下面的规则递归判定：

   | `v` 的来源 | 新鲜性 |
   |---|---|
   | 字面量；`Imm(T)`（深不可变）类型的值 | **新鲜**（不可变对象共享无害） |
   | `new C(a1, ..., an)` | 新鲜 ⇔ 每个 `ai` 新鲜 |
   | 刚从另一个 `Ownership.move()` 解出的值 | 新鲜（独占性由上一环传递） |
   | 局部 `x`（出生点新鲜） | 保持新鲜 ⇔ 从出生到包装，每次向 `x` 的可达字段写入引用时写入的值新鲜；以引用为参数的方法调用按 effects 判定（方法不可达任何全局、参数全部 Shareable/Imm 则视为不引入外来引用），不可判定则视为污染 |
   | 其余（函数调用返回值、字段读取、全局、参数传入） | **不新鲜**，包装即编译错误 |

   典型的编译错误（为什么必须是"整张图"新鲜，见 9.4 节洞一）：

   ```
   error: Ownership.owned() requires a freshly built object graph
     --> main.penguin:12:30
      |
   12 |     let w = Ownership.owned(new Wrapper(g));
      |                              ^ 'new Wrapper(...)' is fresh, but argument
        'g' is a mutable global — the graph would stay reachable on this thread
   ```

2. **消耗检查（运行期）**：`move()` 取出内容后把自己置为 `not_owned`；对 `not_owned` 再
   `move()` 触发运行期错误。语言没有线性类型，编译期无法跟踪消耗，运行期检查够用。
3. **跨线程许可**：通道与创建点把 `Ownership<T>` 当作合法的跨线程元素，无论 `T` 是什么引用
   类型——独占性已经由构造检查（规则 1 的整张图新鲜性）保证，接收方成为唯一持有者。

> **实现状态（2026-10-04）**：规则 1 的表格里"局部 `x`（出生点新鲜）"一行——**逃逸分析
> 已落地**（EmperorPenguin `SemanticBindExpressions.ownership_*`）。接受的线性形态：
> `let mut l = <新鲜初始化子>`（字面量 / new / 另一 Ownership 的 `.move()` / 另一个线性
> 局部，按名环防护），且函数体内该名的其它文本使用全部是**接收者位置**（`l.push(..)` /
> `l.field`，接受为对被转移对象的变更——经典线性类型折衷，9.4 的残余漏洞照记）或
> `==`/`!=` 比较；传参出、别名绑定、字段/全局存储、spawn/lambda 捕获、嵌套块同名遮蔽
> 一律拒绝。表格里更精细的"按 effects 判定方法调用"形式是后续精度步骤。

### 9.3 内容槽私有

`Ownership<T>` 是编译器内建的特殊类型。**内容（`.owned`）的读和写一律在绑定阶段拒绝**，错误
信息指向 `.move()`。否则 `let a = foo.owned;` 就直接漏出了引用，独占性作废。

| 泄漏路径 | 处理 |
|---|---|
| `.owned` 的读 / 写 | 绑定阶段拒绝 |
| 元编程/反射合成的成员访问 | 走同一条绑定路径，同样拒绝 |
| `foo is Ownership<T>.owned` 标签判断 | 允许（纯标签判断，不解包） |
| 包装体本身的传递、存储、经通道发送 | 允许 |
| `let t = o.move();` 之后使用 `t` | 允许（普通局部值）；要再跨线程必须重新包装，`t` 从 move 起重新纳入新鲜性检查 |

### 9.4 两个必须堵上的洞（规则 1 为什么长这样）

**洞一：`new` 不代表整张图都是新的。**

```
let g : mut List<i64> = new List<i64>();        // 全局列表（封闭在主线程域）

class Wrapper { l : mut List<i64>; fun new(mut this, l : mut List<i64>) { this.l = l; } }

initial {                                        // 线程 A（发送方）
    g.push(1);
    let w = Ownership.owned(new Wrapper(g));     // 顶层对象是 new 的，字段却指向全局
    ch.write(w);                                 // 发给线程 B
}

initial {                                        // 线程 B（接收方）
    let wrapper = (wait ch).move();
    wrapper.l.push(99);                          // 与线程 A 的 g.push(...) 同时改同一张表
}
```

如果构造检查只看"是不是 `new` 表达式"，这段代码编译通过，后果分版本：

- **v0（单一全局堆，零拷贝移交指针）**：线程 B 拿到的 `wrapper.l` 与线程 A 的 `g` 是**同一个
  对象**——两个线程同时 `push`，货真价实的数据竞争。
- **v1（跨域复制）**：内存安全保住了（B 拿到的是深拷贝），但**语义静默分叉**：A 继续改自己
  的 `g`，B 改副本——"转移"根本没有发生，两边各自为政，而这正是用户以为 `Ownership` 排除
  的情形。

所以规则 1 的新鲜性必须递归到整张图，且**深不可变的子对象是唯一例外**（它们只读，共享无
害——`new Wrapper("cfg")` 里的字符串字面量不需要复制）。

**洞二：包装类型会随 `T` 变成值类型，被整块复制。**

`Ownership<i64>` 的内容是值样的，于是整个包装会被现有的值分类判成值类型（4.2 节的递归规
则），每次传参、赋值、放进上下文字段都是 `memcpy`。于是父协程和子协程各持一份"owned"状态
的副本，双方 `move()` 都成功，运行期的 `not_owned` 检查永远不会触发——独占性静默失效。

结论：

- 包装类型**强制为引用类型**（堆对象），标签用原子操作做"置位/取值"；
- 转移点（创建点参数、通道写入）编译成**真正的移动**：把发送方的槽位作废，接收方拿到唯一
  引用。

### 9.5 跨域时的两种语义

- **单堆形态（第 10 章 v0）**：对象全在一个堆里，跨域转移零拷贝、直接移交指针——**前提是
  规则 1 的整张图新鲜性检查到位**（9.4 节洞一），否则零拷贝就是零保护。
- **两个堆形态（v1）**：跨域时按"接收方复制一份"处理（与发送方同域时零拷贝）。要说明的是
  这**不是"移动"**：接收方拿到的是副本，身份（指针相同、`__object_id` 相同）不传递，发送方
  的图留在自己的堆里由本地回收器回收。想保持"真移动"的语义，必须在构造点就能证明整张图
  是这次新建的（配合"在共享区分配"或"只被引用一次时提升"）。

## 10. 垃圾回收

### 10.1 v0：一个堆 + 分配锁 + delta 边界停下全世界

第一版最保守：保持单一全局堆，分配按大小类别加锁；回收只在 delta 边界停下全世界，由单线程
标记清扫。枚举全部根（每条线程的主栈、全部协程栈的扫描区、全局根、同步对象内部的引用）。
堆不移动，跨线程指针永不失效。这个版本下所有权转移零拷贝直接安全（前提是 9.2 节的构造检查），
因为只有一个收集器和一份根集合。

**delta 内的分配压力**：一个 delta 可以任意长，而回收只在边界做。分配器设一个硬上限；触碰
上限的协程**停靠在"等回收"上（不计入"可运行"）**。这样全体分配阻塞时系统自然收敛（没有
可运行的活 → 边界到来 → 停世界回收 → 解除阻塞），不会死锁也不会 OOM。

> **实现状态（2026-10-03）**：v0 已全部落地。分配锁与边界停世界收集随 M4b 交付；本段的压力阀
> 见 `std/c/gc.c`（`EMPEROR_GC_HARD_CAP`，缺省 8 GiB、0 = 不限）与 `scheduler.c`
> （`_emperor_sched_alloc_park` + 边界释放）。边界收集后"活集 + 最小待决 charge"仍放不下时
> 判定确定性 OOM（退出码 62，经 `exit()` 通道）——判定必须含 charge，否则停靠者卡在
> "活集"与"活集+charge"的缝隙里永久循环（实测保活循环恰好停在 cap−48）。阀门只在 mt 内核
> 下停靠；经典调度器路径行为与改动前逐字节一致。实现细节见 impl-notes 30"分配硬上限压力阀"。

### 10.2 v1：两个堆

- **线程本地堆**：只有本线程访问，本地回收器回收，廉价、频繁。
- **共享堆**：可能被多个线程访问的对象，由全局回收器在停下全世界时回收。

对象默认分配在本地堆；**只在明确的移交点**把它（的值）放进共享区。这样做的理由是：字符串
这类不可变对象是运行期最高频的分配，如果一律进共享堆，短命字符串的垃圾会全部堆在只有全局
回收器能收的地方，反而让全局回收变频繁。

注意在决定 A 之下，**不需要**"按执行上下文决定这次分配进哪个堆"这套路由：已启动的协程不会
换线程，它的本地分配永远对本地回收器可见，跨线程交接只发生在显式的移交点上。

> **实现状态（2026-10-04，v1 第一级已落地）**：每线程分配 arena + 无锁小对象快速路径
> （gc_span.c `GtArena`：每大小类 current span + 线程本地 quarantine 环；span
> 退役/补充/超块仍走全局锁，每 span 一次而非每分配一次；隔离环随线程走——边界收集时多个
> arena 可同时持有在途临时对象）。收集器保持**一次停世界扫全部 arena**，因此本阶段**无需**
> 移交点提升：跨线程指针全部在停世界时刻被同一份根集合覆盖。双域（本地回收器 + 共享堆 +
> §10.3-10.6 移交点提升）为下一阶段。两个顺带修复：慢路径紧急收集移出分配锁（finalizer
> 分配会重入不可重入锁——旧代码的潜在死锁）；malloc 路径的 8× goal 紧急收集同样出锁。
> 性能（tinyriscv 经典形态，交错 A/B）：发布配置（OPT=-O2 运行时）下 arena 相对 v0
> 分配锁净赚 ~1.4%，分支经典路径总回归从 +4.7% 收窄到 **+1.1%**（余量为 mt 内核链入
> 经典二进制的代码体积/布局效应）；-O2 也就此定为运行时默认（原默认 -O0 白慢 ~12%）。

### 10.3 移交点清单（封闭集合）

- 可偷创建点的上下文字段填充（固定创建点不是移交点，同线程）；
- 同步通道的写入；
- `Ownership` 的移交；
- 全局变量的初始化与写入全局的同步对象；
- **可偷创建点的结果容器 `complete()`**（子协程把结果写回父协程，这一处容易漏）。

### 10.4 提升怎么做

在移交点上，把值放进共享区有两种做法：

- **唯一引用的新对象**（创建点的上下文对象、`Ownership` 包装体）：直接在共享区分配，或者
  确认只被引用一次后搬过去。
- **已经被多处引用的不可变对象**（比如同一个字符串既在本地容器里、又要写进通道）：**按值
  语义复制一份进共享区，不保持身份**。不可变对象的子节点在构造时就冻结了，所以复制之后
  共享区里的那份永远不会再指向本地堆。字符串是扁平结构，复制是常数时间。

这条要求做一次审计：程序里不能有依赖"同一个对象在不同线程里身份相同"的代码（按地址哈希、
`__object_id` 比较之类）。审计结论写进规范。

### 10.5 为什么不需要写屏障

写屏障是"每次往堆里存指针都要检查一次"的开销，用来维持"共享对象不指向本地对象"。本设计
里这条方向不变式靠两件事成立：

1. **不可变对象**：子节点在构造时冻结，"提升时复制一遍"之后永远不指向本地堆。
2. **可变对象不共享**：语言层面不存在"共享的可变对象 + 普通字段赋值"这个组合——

   - 同步对象（`Sync`）及其内部节点恒在共享堆，它们的一切变更发生在已经持锁的方法内部；
   - 跨域的 `Ownership` 移交按 9.5 节处理（复制或真移动），不会出现"共享对象持有本地对象"；
   - 其它可变对象只被单线程访问（INV1），不涉及跨堆指针。

于是本地回收器把共享对象当作不透明对象处理（不释放、不穿透追踪），只回收本地堆即可。

### 10.6 不变式集（v1）

1. 同步对象及其内部节点恒在共享区；它们的一切变更发生在已持锁的方法内。
2. 不可变对象默认在本地堆，移交点复制进共享区；子节点冻结 ⇒ 共享区里的不可变对象永远不会
   指向本地对象。
3. `Ownership` 跨域按 9.5 节；同域零拷贝。
4. 移交点清单（10.3 节）是封闭的：语言层面不存在清单之外的跨线程引用流。

### 10.7 终结器要回到对象的"老家"执行

实现了内存释放接口（`IMemoryDispose`）的对象，今天由回收器在清扫时直接调用它的释放函数。
并行之后，释放函数是用户代码，可能在另一个域里操作本地资源，所以必须**延迟到该对象所属的
域**执行。这会改变可观测的时序（关闭文件的时刻），相关测试要按新时序调整。

### 10.8 根集合

停下全世界之后枚举：每条线程的主栈（水位协议照抄现在主线程的做法）、全部协程的栈扫描区
（跟句柄走，句柄不跨线程所以不需要额外握手）、全局根、同步对象内部的引用、元编程钉住的
对象、新对象隔离环。

## 11. 明确不做、或暂不做的做法

| 做法 | 处置 | 原因 |
|---|---|---|
| 给普通字段加"延迟提交"修饰符 | 不做 | 值类型会被整块复制，挂起状态跟着副本走；布局元数据与扫描一并变贵（6.6 节） |
| 用"时间先后"给同 delta 多写者定序 | 不做 | 并行下"先后"本身未规定；只能按写者身份定序（6.5 节） |
| 把全局变量静态分组、每组一条线程 | 不做 | 偷取是运行期事件；运行时别名让分组单位必须是对象图（4.3 节） |
| `wait cond` / `wait change(x)` | **删除语法** | 没有唤醒源（写条件的协程不知道谁在等它），只能每个 delta 边界全体重查；等状态用通道/事件/信号表达（0.3、8.2 节） |
| `ICopyCross`（显式深拷贝类型"按用户拷贝过界"） | 暂缓 | 不进共享格它就是死特性（哪里都过不去）；等 `Ownership` 实测后再决定是否作为"发送侧调用 `copy()`"加入 |
| 静止指纹退出（"状态两个 delta 不变即结束"） | 退役 | 退出改看"所有协程是否结束"，不需要猜（7.4 节） |
| 自动检测死锁/永久挂起 | 暂不做 | 区分"正常等待"与"卡住"要猜用户意图；第一版选择"只要还有协程活着，程序就活着"，将来再优化（7.4 节） |
| 动态冻结（观察到没人持有可变引用就共享） | 挂起 | "没人持有"不可靠：可变性是逐绑定的权限而不是对象状态，别名集合运行时不可枚举；每次字段赋值加检查的税与 `Ownership` 覆盖重叠 |
| 跨域零拷贝 + 存入写屏障 | 挂起 | 写路径税；先用"接收方复制"（9.5 节），待实测数据 |
| 在运行时自动识别"新鲜值"并当作可转移 | 不做 | 违背"转移必须显式"，改为编译期检查构造点（第 9 章） |
| BabyPenguin 虚拟机实现多线程 | 不做 | 只有原生实现做多线程（与 io 标准库同例）；跨编译器的一致性由 sim 形态保证 |
| 让固定创建的父协程把"等待点"也钉住 | 不需要 | 决定 A 已经保证父协程不会搬家（3.2 节） |

## 12. 运行时工程要点

- **补齐原生原子操作**：C11 `__atomic` / Windows Interlocked 实现 `AtomicI64`/`AtomicBool`/
  `AtomicU64`，接口与 BabyPenguin 现有内置对齐（原生路径目前一个原子操作都没有）。
- **同步原语**：互斥锁（pthread / SRWLock）、停靠-唤醒（futex / WaitOnAddress）。Windows 侧
  走 SRWLock + 条件变量，维持"不引入 winpthread"的既有链接约束。
- **阻塞型同步操作一律让出协程**（5.6 节），互斥锁内含停靠队列。
- **把 C 微内核逐线程化**：调度上下文、创建收件箱、主栈水位、运行队列从单全局改为每线程
  （第一版用互斥锁版队列，无锁双端队列后置）。
- **收敛判定要跨线程**：delta 边界条件是"全局再没有任何可运行的活"，实现上需要一个跨线程
  的判定（各线程队列空 + 在飞工作清零 + 分配阻塞者不计入），并且要处理"决定收工前后再检
  查一次"的竞态，否则会漏掉刚投递进来的活。
- **边界七步就是调度器主循环**（0.2 节）：提交延迟写 → 触发到期定时器 → 有活就同 tick 下
  一个 delta → 非阻塞探测 fd → 推进时钟 → 阻塞 poll → 退出判定。其中"分配阻塞算停靠"
  （10.1 节）也要并入收敛判定。
- **定向唤醒**：停靠的协程不能搬家，唤醒必须投递到它所属线程的队列（3.2 节第 4 条），所以
  每条线程都需要可被打断的等待（`eventfd` / self-pipe / `WaitOnAddress`）。
- **条件等待原语**：所有"等条件"（通道、结果容器、事件、互斥锁）都实现成"条件满足即在当前
  delta 内恢复"，不要保留"每个 delta 问一次"的轮询（8.3 节第 4 条）。
- **两类停顿诊断**：(a) 一个 delta 长时间收敛不了（两个协程互相唤醒的活锁，或者某个协程在
  `while (!cond) wait -1;` 里自旋）；(b) delta 在不停收敛但**虚拟时钟长时间没前进**，而还有
  协程在等时间（例如 `while (!cond) wait;` 的重试循环把 tick 钉住，0.3 节）。给明确的诊断
  信息（delta 数/收敛步数预算 + 提示"疑似零时间循环"），不要无声挂起。
- **`exit()` 广播**：并行形态下任何线程调 `exit()` 都要设置全局停止标志并唤醒全部线程，在
  下一个 delta 边界统一退出；被偷协程里的未捕获异常按同一通道上报。
- **语法变更**（M0，两个编译器必须同步改）：
  - 删掉 `'wait' expression 'tick'` 产生式（`BabyPenguin/Parser/PenguinLang.g4:42`）与
    BabyPenguin 的对应重写分支（`BabyPenguin/SemanticPass/06_SyntaxRewriting.cs:398`）；
  - 删掉 `wait cond` / `wait change(x)` 的解析与重写（同文件）；
  - 为负数写法加降级路径（字面量可以编译期直接降到"让出"，运行期才知道符号的走运行期
    判断）。
- **标准库要改写的三处**（今天它们都靠"让出一次"来换取延迟或重试；统一成"给 tick 设卡"
  之后，这些地方会把时间钉住，必须改成条件等待或显式延迟交付）：
  1. `Fifo.write` 的背压 `while (is_full()) wait;` → 条件等待（**这是正确性要求**：通道满时它
     会把 tick 钉住，任何"等时间"的协程都醒不过来，见 0.3 节）；
  2. `Event.emit` 末尾的裸让出 → 显式的延迟投递（边界提交）；
  3. `IFuture.do_wait` 的"让出再问一遍" → 条件等待（完成时唤醒）。
- **BabyPenguin 的 C# 调度器同步对齐（已落地，2026-10-03）**：新语义（完全收敛的 delta、
  边界七步、新退出规则、`wait;` 设卡、负数让出）是**语言语义**，参考实现必须一起改，
  否则跨编译器测试全部失准。SimScheduler 重写为七步边界（停靠分三类：裸 wait 欠 delta /
  负数让出重排当前 delta / 条件停靠只等唤醒；停靠类别经侧信道标记传递——extern 紧挨
  `wait` 置标记，调度器归档时消费）；do_wait 先 poll 快路径；`wait n` 经 `_wait_ticks`
  运行期符号分支；Fifo 背压改条件停靠（不设卡）；通道投递/消费/关闭走边界延迟唤醒
  （观测时序与经典轮询一致）；协程完成即唤醒（同 delta，与 mt 相同）；两条停顿皮带
  （EMPEROR_SCHED_STEP_BUDGET / PIN_BUDGET，退出码 60/61，旋钮与原生同名）。
- **顺序回退平台**：无 ucontext/fiber 平台的顺序执行路径（`__sim_time_travel`，
  `scheduler.penguin:734`）要随边界七步一起改。
- **外部输入轮询归属单一指定线程**，事件分发负责唤醒目标域的队列。
- **句柄销毁只由属主域执行**（或按 delta 延迟回收）。
- `print` 加锁保证整行原子；对象 id 计数原子化。
- **跨动态库的创建一律固定**：库元数据目前不携带副作用信息，等元数据加入 effects 字段后再
  放宽。
- **元编程调用（`#fun`）第一阶段一律固定**。

### 12.1 已落地的工程教训（M4b 调试记录，2026-10-04/05）

这些是 sim-mt 并行化过程中真实踩过、已修复并锁进测试的坑，后续动调度器内核时先读这里：

1. **幻影队列项（最高优先级教训）**。不变式：`queued=1 ⟺ 恰好一次入队且不在执行`。两条
   破坏路径都源于"协程运行中却被 wake 推入运行队列"：(a) `_co_switch_in` 不识别
   CO_RUNNABLE 状态落进 PARKED 分支，owed_push 用 qnext 二次挂链，运行队列从此处截断或
   成环（丢失唤醒 → exit 63；环 → 偷取扫描持锁死循环；双重入队 → use-after-munmap）；
   (b) do_wait 的 poll-then-register 窗口丢 kick。修复：状态 8（"wake 的 push 即重排"）+
   `_emperor_mt_wake` 的状态检查与 push 同锁临界区 + future register/unregister/cancel
   三件套（Mesa 顺序：先声明 CO_COND 入 futures、再 poll、ready 则 cancel 反提取幻影）+
   销毁前 `mt_unfile_runq_phantom` 摘除幻影。
2. **帧链头必须 TLS，且不能用 IR 级 thread_local**。`_emperor_gc_frame_head` 是普通全局时，
   N 个 worker 并行换栈互相践踏帧链（8 线程 100% 复现 "CORRUPT REF-MAP" abort）。修成
   `_Thread_local` 后**发射代码必须走 C 访问器**（`_emperor_gc_frame_get/set`）——
   IR 级 thread_local 全局会被 JIT/ORC 解析成 emutls 克隆，与宿主 ELF TLS 不别名，
   `make bootstrap` 直接报 `__emutls_v.*` 未定义。这条弯路已走过，别再走。
3. **收敛判定必须显式检查队列空**。全员醒着的协议里"有人排队 ⟹ 它的属主在循环 ⟹ 不可能
   停满"是隐式成立的；一旦允许 worker 停着睡过 delta（between_parked），推入方就必须
   在锁内解除停靠计数并持锁发信号，且收敛判定加上"全部运行队列空"——否则边界会带着
   未处理的工作收敛（实测：多核 tinyriscv 丢 2 个 UART 字符、提前 7728 周期报结束）。
4. **协程切换的隐藏系统调用**。glibc swapcontext 每次做 2 次 rt_sigprocmask（POSIX 信号
   掩码语义），而本运行时从不改协程信号掩码——高频 wake/重停靠场景下这是可测的主项
   （113 万次/15 秒）。x86-64 用顶层汇编直换 callee-saved 寄存器 + MXCSR/x87 控制字
   （注意：x86 没有 naked 函数属性，C 包装函数的序言会先污染 callee-saved 寄存器，
   必须整函数手写汇编）。
5. **自旋要批量化读共享谓词**。每个 pause 轮询一次 `runq_head` 之类的共享缓存行，
   8 个自旋线程会把队列头缓存行打成乒乓（干净构建越跑越慢、带 trace 反而稳定——
   stderr 串行化掩盖了争用）。每 32 次 pause 读一次，轮询率降 30 倍、延迟仍在百纳秒级。
6. **watchdog 不能拿死锁**。看门狗的转储路径若先 `pthread_mutex_lock(mt_glock)`，
   恰好在"glock 卡死"这一它要暴露的故障上自己噤声——必须 trylock，EBUSY 时裸读
   互斥量内部（glibc 布局稳定）报出 owner TID。
7. **`_sched_sync` 单线程门控**。N=1 时 test-and-set 永不竞争，但每次持锁仍烧一整轮
   yield 往返（suppression trace 里 state=6 的主体）。`_mt_nthreads() < 2` 时整个协议
   跳过（nthreads 在 worker 启动后固定，门控两侧一致）。
8. **TSAN 验证纪律（2026-10-05，N=1/2/4 零告警验收通过）**。三条教训：
   (a) **手写汇编切换必须被 TSAN 构建排除**——glibc swapcontext 的 TSAN 拦截器
   承担线程状态交接，raw asm 会静默跳过它（每次恢复都误报）；co_swap 用
   `__has_feature(thread_sanitizer)` / `__SANITIZE_THREAD__` 守卫回退 glibc 路径。
   (b) **同一位置的原子/普通混合访问本身就是竞争**：给自旋提示读加了原子读之后，
   TSAN 反而报告锁内普通写与它的配对（C++11 语义下混合访问即 UB）。凡是自旋
   碰过的字段（runq_head、mt_delta_running、mt_stop、idle/between_parked、两种
   停靠计数、co->state、owner_idx）必须**全量**原子化（relaxed 足够——排序由
   glock 握手或自旋后的持锁复查提供）。
   (c) **TSAN 抓到一个真 bug**：GC 扫描区域注册表完全无锁——任意线程 mid-delta
   的 co_create 注册栈、任意线程的 destroy 注销、每次停靠收窄，全部并发裸奔；
   两个并发 add 会写同一槽位且计数 +2 丢一个区域 = 未注册的协程栈不被扫描
   = 存活对象被提前回收。修复：gc.c 专用 region mutex（教训中的教训：被加锁
   函数有三个早退路径，第一版全部持锁 return——第二次调用必死锁）。
9. **唤醒归档的五个连环洞（2026-10-06，N=8 错结果根因）**。"协程已注册、
   正执行 poll"的窗口与 park 路径之间没有原子性：① `mt_switch_away` 不声明
   状态就挂起（争用让步把 CO_COND 覆写成 CO_YIELD → 状态阶梯 fallthrough 误
   归裸 wait，钉死时钟）；② kick 无条件消费 futures 表项（让步中的等待者被
   吃掉 → 丢唤醒）；③ owed 与运行队列共享 qnext（双重归档自环链）；④
   register→poll→park 中 poll 让步吞掉唤醒的幻影队列项（park 时两处归档皆
   空 → NOWHERE 丢模块）；⑤ between-delta 谓词拒绝在队列非空时停泊（无痕
   忙自旋烧满核）。修复模式：**挂起必带 park 态**（切换点声明 CO_COND）、
   **注册幂等 + 归档与令牌分离**（见第 10 条）、**每条链表专用链接字段**
   （qnext/onext/fnext 各管各的）、**边界自愈兜底**（把"停泊却无处可寻"
   修复为一次伪唤醒——do_wait 按设计容忍伪唤醒，残余交错从丢失降级为一拍
   延迟）、**状态阶梯显式断言**（exit 66，宁可炸也不 fallthrough）。
10. **no-consume futures 协议（2026-10-07，64a73086）**。futures 表项是等待者
    整个 do_wait 的**停靠归档**，不是一次性消费令牌：kick 只把 CO_COND 翻成
    RUNNABLE（队列推送），**绝不摘链**——表项只由等待者自己的退出路径
    （unregister/cancel/destroy）在锁内摘除。旧"消费-再注册"握手有一条修
    不死的缝：任何背着 runner 摘链的路径都会留下 in_futures=1 却无处可寻的
    协程（每 ~16 周期一次的自愈轮询，修复晚于管线深度时就是丢字符误执行）。
    表项常驻后，**停泊的注册等待者构造上可寻**；`state == CO_COND` 就是
    "需要唤醒"的纪元标记。
11. **pop→RUNNING 的幻影窗口（2026-10-12，free-mt exit 63/轮屏障失效）**。
    `mt_runq_pop_locked` 持 glock 出队，`_co_switch_in` 的 CO_RUNNING 置位却在
    锁外——两步之间的 wake 读到合法幻影停靠者**陈旧的 CO_COND**，"生效"并
    给一个即将恢复的协程再压一个幻影；恢复者的 cancel 因状态已是 RUNNING
    （≠ RUNNABLE）跳过摘除，陈旧幻影残留（queued=1）。下一次裸 `wait 0` 的
    owed 归档被"dup refused"拒绝，协程被自己的陈旧幻影**同轮复活**——轮
    屏障被破坏，发射可以早于 waiter 重订阅，事件丢失、协程永久停靠。修复
    模式：**出队与 RUNNING 声明同一临界区**（wake 在窗口内看到 RUNNING →
    无操作，即将到来的恢复-重轮询按 Mesa 语义吸收它）；cancel 改按
    `queued` 标志摘幻影（RUNNING 协程带队列项 = 不变式破坏，一律修复）。
    顺带：策略文件派生（mt→free-mt）时逐函数核对锁纪律——unsubscribe
    就是在派生时丢了 `_sync_begin`（mt 版有、free 版无），单靠 review 不会
    发现，靠的是"ambient EMPEROR_THREADS=4 跑全部子集"这一步。
12. **co_all_head 是全线程共享的链表（2026-10-12，SIGSEGV）**。co_create
    建链在 spawn 线程、_emperor_co_destroy 摘链在收割线程，都在 delta 中段
    并发；无锁变异下两次并发摘链丢更新，链上残留已 munmap 的节点，边界
    自愈/idle-dump/destroy-all 的下一次遍历读已释放内存（coredump 定位
    mt_scan_lost_parked → co_state_get）。修复：mt_kernel_seen 后建链/摘链
    持 glock（经典路径与内核启动前的 main 单线程免锁）。同类教训：**全线程
    可达的记账字段一律 RELAXED 原子**——gc_poll 的 STW 时钟/轮询计数/
    采集点、mt_live_count 都是回边安全点普及后才变热的，普通读写被 TSan
    一次抓了 3.4 万条；且注意 **TSan 的进程退出码是 66**，与调度器状态阶梯
    断言的 exit 66 撞号——先看 stderr 的 "park-state invariant violated"
    再定性。

## 13. 测试与验证

### 13.1 三档断言

| 测试类型 | 断言方式 |
|---|---|
| 单线程形态（sim）、且输出与 delta 内顺序无关 | 逐字节比较输出（现有方式，继续用） |
| 并行形态、只保证"输出行集合" | 行集合比较（计划的 `SORTED` 模式） |
| 依赖时间位置的用例 | **必须改写**：把断言放在显式同步点（推进 delta / `wait n;` / `wait f`）之后，不要在隐含的边界上观察 |

### 13.2 需要审计与改写的现有用例

M4 之前要逐例过一遍，分五类：

**(1) 依赖"同一个 delta 内多协程先后"的**：当前的 AsyncTest / PortTest / TimingTest / ChannelTest /
MultiInputTest 共 89 个用例里，按今天语义实测真正依赖同 delta 先后的有 5 个：
`MultiInitialRoutines`、`AsyncSimple`（期望 `12`，依赖"创建后本 delta 排在打印之后"）、
`AsyncEventReceiver`、`OnEventClass`、`FifoBackpressure`。其中 `FifoBackpressure` 的逐字
节期望在新语义下不再成立（`w 1 / w 2 / r 1 / w 3 …` 与 `w 1 / w 2 / r 1 / r 2 …` 都合法），
只能改成集合断言或在显式同步点上断言。**注意：这份清单是在今天语义下筛的；新语义下条件
等待会在同一个 delta 内唤醒，产生今天不存在的同 delta 交互，审计必须在新调度器上重做。**

**(2) 依赖"静止即退出"的**：新退出规则下（7.4 节），"某协程永远等着、其他协程跑完就退出"
的用例会挂起。属于这一类的有 `QuiescentBlockedWaiter`、`WaitConditionNeverTrue`、
`UnconnectedInputWaits`，它们要改成显式结束；其余以"永远等待的接收者"结尾的用例要在 M4
审计时逐个确认。

**(3) 语义虽变但用例仍通过**：`BareWaitLoopSurvives` 这类"裸让出循环不会被误判为静止"的
用例，在指纹退役后不再需要它的原始回归目标，但断言本身（循环正常跑完）继续有效。

**(4) 语法删除的直接受害者**：`wait ... tick` 32 个文件 42 处（机械改写）；`wait change(x)`
3 个文件（`WaitChangeVariable`、`WaitChangePort`、`PortBareReadSettlePoint`）与
`wait cond` 3 个文件（`WaitCondition`、`WaitConditionNeverTrue`、`PortConditionWait`）要改写
成通道/事件/信号表达后保留测试意图。

**(5) 等条件用"让出再试一次"实现的写法**：`while (!cond) wait -1;`（自旋，delta 永不收敛）
和 `while (!cond) wait;`（每 delta 重试，但把 tick 钉住）在新语义下都会让时间停住，必须改成
条件等待（0.3 节）。

### 13.3 顺序扰动检测进 CI

`--shuffle-deltas=SEED`（6.8 节）用多个种子跑同一程序并比较输出，任何差异都指向"这个程序
依赖了 delta 内的顺序"。这是替代"全局确定性承诺"的主要手段，也是判断"我有没有用对构件"
的工具。

### 13.4 差分测试的正确用法

- `sim` 与 `sim-mt --threads=1` 逐字节一致：保留，作为**回归锚点**（验证串行路径没退化）。
  注意它只覆盖串行骨架，不能验证并行语义。
- `--threads=N>1` 与单线程"行集合一致"：只对**与 delta 内顺序无关**的程序成立，必须由用例
  作者保证，测试框架无法代劳（6.2 节的例子就是一个反例：行序与行集合都不同）。
- 因此并行类用例的写法规范是：**在显式同步点断言**，或者在测试描述里声明"本用例的输出与
  顺序无关"。

### 13.5 其它

- ThreadSanitizer（`-fsanitize=thread`）构建进 CI 周期任务；Windows 用 WINE 冒烟。
- 随机任务图压测（创建深度、星型通道、全局触摸模式的组合），配合域标签断言。
- 调试模式的对象头域标签抽查，作为静态分析的纵深防线。

## 14. 结论与开放问题

设计收敛为一个封闭的模型：类型层面的共享格（同步 / 不可变 / 可共享值 / 所有权）驱动编译期
的封闭分析与条件同步；运行时以"tick + delta tick"两层时间组织并行（delta 内就绪即恢复，
delta 边界七步收口）；垃圾回收用"本地堆 + 共享堆"两级并且全程不需要写屏障。所有安全性论证
最终落在两个前提上——**不可变性**（不可变对象可以共享，且子节点冻结）与**独占性**（所有权
转移安全，提升无竞争；构造检查验证整张图新鲜）。

确定性不作为语言承诺，而是作为**程序性质**提供：延迟提交构件 + 编译期诊断 + 顺序扰动检
测器。

开放问题：

1. 延迟提交在自由形态（free-mt）里怎么处理：禁用，还是接受"提交点在系统空闲时发生"（6.7 节）。
2. `Fifo` 默认改成延迟提交的时机与迁移路径：它会影响现有测试期望、BabyPenguin 参考实现的
   通道语义（两边目前是"同名同形状"），需要一起决定。
3. 多写者信号/连线的合并规则集合（按端口号、按创建序号、用户分辨函数）与默认值；多等待者
   通道的按身份定序（6.9 节）。
4. 组迁移（一组的对象图整体过户并带走固定协程）的设计。
5. 动态冻结的重新评估条件：如果实测写路径税低于估计，或"接收方复制"成为瓶颈。
6. `Ownership` 深拷贝的环检测在大图上的开销。
7. 自由形态（free-mt）的完整设计：没有 delta 之后，退出协议、唤醒协议、以及"提交点"的替代
   定义。
8. 循环回边安全暂停点检查的代码生成细节（只有自由形态需要）。
9. 库元数据加入副作用字段之后，跨库创建的放宽规则。
10. 挂起诊断（"还有哪些协程在等什么"）的实现方式（7.4 节，暂不承诺，但排查问题时很有用）。
11. `ICopyCross` 是否作为"发送侧调用用户 `copy()`"加入共享格（11 节暂缓项）。
