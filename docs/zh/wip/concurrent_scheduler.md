# 并发调度器设计（WIP）：自动多线程调度与线程封闭模型

> 状态：**草稿（work in progress）**。本文描述的是计划中的机制，当前编译器与运行时尚未
> 实现其中任何并发部分。文中"现状"章节描述的则是当前代码的真实行为。设计仍在演进，
> 定稿后本文将移入 specifications/ 并补英文镜像。

## 摘要

本文给出 PenguinLang 多线程调度器的完整设计论证。设计目标可以概括为三条原则：
**调度完全自动**（用户程序中不存在线程概念）、**用户不关心线程**（放置决策由编译器与
运行时做出）、**正确性优先于效率**（任何调度决策都不允许引入数据竞争）。

核心机制是一个编译期的**线程封闭**（confinement）分析：协程在创建点被静态分类为
**可偷取**（stealable，可被任意线程执行）或**固定**（pinned，永远在出生线程执行）。
分类依据是一个类型层面的共享格：深值类型与深不可变类型可以跨线程，实现了 `ISync`
接口的类型可以跨线程，其余引用类型一律封闭在单个线程内；跨线程转移引用只能通过
`ISync` 容器（元素必须是可共享的）或显式的 `Ownership<T>` 所有权转移。

在此之上，本文论证三件事：其一，现行 delta-round 离散事件仿真语义可以与多线程并存，
条件是采用整体同步并行（BSP）结构——仿真时刻全局统一，轮内并行、轮界全局屏障，这正
是 SystemC 对同一 delta 内求值顺序不加规定的立场；其二，垃圾回收器可以在不引入写屏障
的前提下拆分为线程局部回收与全局回收两级，关键依据是封闭模型同时封死了"共享对象指向
线程局部对象"的指针方向；其三，`#specializing` 可以让通道族按元素类型条件性地实现
`ISync`，使封闭在同一域内的通道保持今天的无锁实现。

## 1. 引言

### 1.1 目标与三原则

PenguinLang 现有的并发模型是单线程协作式协程。本设计要回答的问题是：同样的程序如何
在不引入任何用户可见线程概念的前提下使用多核。三条原则贯穿全部设计决策：

1. **自动调度**：放置（哪个协程在哪个线程上运行）由编译器与运行时决定。
2. **用户不关心线程**：语言不提供 `spawn_on`、锁的获取顺序调优等线程级控制；并发
   正确性不依赖用户的自觉。
3. **正确性 >> 效率**：宁可全部固定、放弃并行，也不接受一个可能产生数据竞争的优化。

### 1.2 "正确性"的精确定义

本设计把"正确"限定为两条可验证的性质：

- **无数据竞争**：对任何非同步对象的可变访问只发生在单个 OS 线程的执行流中。
- **无内存错误**：垃圾回收器不会回收仍被引用的对象，也不会让指针失效。

以下性质**明确不在承诺范围内**（与 Go 语言的正确性观一致）：

- 执行顺序的确定性（并行形态下协程交错不确定，见第 6 章）；
- 免死锁（错误地嵌套获取多个同步锁仍会死锁，调试模式提供检测）；
- 免饥饿与免活锁。

死锁与确定性在单线程仿真形态（sim，见 6.4 节）下天然保持，该形态继续作为默认。

## 2. 背景与现状

本章描述当前代码的真实行为，是后续论证的事实基础。

### 2.1 并发运行时现状

- 协程是**栈式**（stackful）的：`EmperorPenguin/std/c/scheduler.c` 用 ucontext（POSIX）
  或 Win32 fiber 实现 `__Coroutine` 句柄的创建、切换与销毁，每个协程拥有 mmap 分配的
  独立栈。调度策略层（就绪队列、定时器表、虚拟时钟、quiescence 检测）是 Penguin 代码
  （`std/penguin/scheduler.penguin` 的 `__sched_run`），C 侧只保留上下文切换微内核。
- 协程的创建面是 `async f(args)`。编译器把 spawn 重写为一个合成的上下文类
  `__SpawnCtx_<n>`（字段即各参数）加一个 `__SpawnFuture<R>`（父协程持有的结果容器），
  运行时经 `_co_spawn_entry(ctx)` 启动。
- 通信原语是普通 Penguin 类：`Fifo`（FIFO 队列）、`LatestChannel`（线语义，同轮多写
  坍缩到最终值）、`MergeChannel`、`_Fanout`（输出端口扇出）、`MultiInput`（扇入）、
  `Event`（广播）。它们内部没有任何同步机制，依赖单线程事实。
- `wait` 表示停靠一个 delta 轮；通道满时的背压就是 `while (is_full()) wait;` 轮询。

### 2.2 delta-round 仿真语义

调度循环按 **delta 轮**（delta round）推进：每轮执行轮开始时排队的全部协程（停靠者
进入下一轮队列），然后触发到期定时器；无进展时把虚拟时钟 `_sim_now_tick` 跳到最早
的定时器截止点；存在 fd 等待者时阻塞在 `poll()` 上等待外部事件；全部静止时用**静止
指纹**（对每个存活协程冻结栈的哈希按收养序合并）连续两轮不变来判定程序结束。轮内
执行顺序是确定的（FIFO），现有异步测试的字节精确断言依赖这一点。

### 2.3 类型系统背景

- 类被分类为值类型或引用类型（`SemanticClassifyValueTypes.penguin`）。自动分类要求
  **所有字段都是值样的**（递归检查，含枚举 payload 与泛型参数）；但显式
  `impl IValueType` 的类直接判为值类型，**不检查字段**——它可以携带引用字段。
- 值拷贝语义已经落地：值类型在绑定、参数传递、成员提取时一律复制；`mut` 只是编译期
  修改权限，不影响内存布局。复制是**槽位级**的：值类里的引用字段（如 `string`）复制
  的是指针，两个副本共享所指对象。
- `string` 在分类层被当作 primitive 值类型，在 LLVM 输出层是 GC 堆上的指针
  （`ref<string>`）。它安全跨线程的依据是**不可变性**，不是"值"。字符串字面量是编译期
  常量，不进入分配器；运行期字符串操作（`+`、`to_string`、子串、文件读取）都分配新
  对象。
- fun value（函数值闭包）恒为引用类型；接口类型的值经装箱（box）成为堆引用；未实现
  `IReferenceType` 的接口大小未知，只能作为局部变量或参数存在。
- 原生路径（EmperorPenguin → LLVM → C 运行时）**没有任何原子操作**：`AtomicI64` 只存在
  于 BabyPenguin 的 C# 虚拟机内置函数中。

### 2.4 GC 现状

green tea 回收器（`std/c/gc.c`、`gc_span.c`）是保守扫描式：根集合包括各线程……目前
只有主线程的主栈（经水位标记协议）、每个协程的栈（注册为扫描区）、全局根。堆是全局
单一段堆（span heap），按大小类别管理槽位，位图清扫；对象**从不移动**（整个 span 空
了才整体回收，malloc 大对象走独立路径）。全部状态是单线程静态变量，没有任何锁。

## 3. 基础方案与它的本质

### 3.1 基础方案

设计的起点是如下提案：

1. 调度器基于**工作窃取**（work stealing：空闲线程从其他线程的任务队列尾部取走任务
   执行）。
2. 活动协程产生的新协程默认属于当前线程。
3. 创建时分析新协程获得的变量输入：只持有值类型的协程可被调度到其他线程；从当前协程
   获得任何引用类型的协程固定在当前线程。
4. 编译后对所有全局变量自动分组，每组可分配到不同线程。
5. 只有实现了 `ISync` 的引用类型可被多线程共享（如原子量、互斥锁、异步队列）。

### 3.2 本质与先例

该方案的本质是三件事的叠加：**Rust `Send` 约束的保守自动推断**（推断而非要求用户标
注）、**Pony 引用能力的粗粒度化**（只在创建点与转移点检查，而非每个表达式）、
**Erlang/Go 的"跨线程只经同步原语"纪律**（但由编译期强制而非运行时检测或惯例）。
已有系统的对照：

| 系统 | 对应机制 | 与本设计的差异 |
|---|---|---|
| Rust | `Send`/`Sync` trait | 我们推断而非要求标注；没有唯一性借用，跨通道传引用需 `Ownership` |
| Pony | 引用能力（iso/val/tag） | Pony 编入类型系统每个表达式；我们只在边界点检查 |
| Erlang / Go | 进程间只经消息 / "不要通过共享内存来通信" | 我们编译期拒绝违规而非运行时警告 |
| SystemC | delta cycle 内进程求值顺序不规定 | 第 6 章 BSP 模型的直接先例 |
| Java 虚拟线程 | 不可变对象自由共享 | 我们编译期判定不可变性，不依赖运行时 |

## 4. 形式化模型

### 4.1 域与放置

**域**（domain）指一个 OS 线程所执行的全部固定协程及其对象的集合。放置规则：

- 协程默认属于创建它的线程（亲和性，affinity）；
- 标记为可偷取的协程可被任意线程取走执行；
- 持有不可共享引用的协程不可偷取，永远在出生线程执行。

### 4.2 共享格

以下谓词全部可以由编译器从绑定后的类型树计算（规划中的 Pass 10）：

```
Sync(T)      : T 实现了 ISync 接口
Imm(T)       : 深不可变 —— primitive（含 string）；不可变枚举且所有 payload 为 Imm；
               不可变类且所有字段为 Imm（含泛型参数不可变）
ValueShare(T): T 是 IValueType 且所有字段 Shareable（编译器递归检查，不信任标记本身）
Own(T)       : T 是 Ownership<U>（第 7 章；构造点已验证独占性）
ICopyCross(T): T 显式实现 ICopy<Self>（用户亲手写了拷贝函数）

Shareable(T) : Sync(T) ∨ Imm(T) ∨ ValueShare(T) ∨ Own(T)
```

各成员的语义：

- **按引用共享**（多个线程同时持有同一个对象）安全当且仅当 `Sync ∪ Imm`。string 属于
  Imm：它是不可变堆对象。
- **零拷贝迁移**（协程栈整体被偷走，值随栈移动；spawn 上下文字段携带）安全当且仅当
  `Shareable`。
- **按用户拷贝过界**：`ICopyCross` 类型在线程边界处调用用户实现的 `copy()`，接收方得
  到副本。信任挂载在用户亲手写的拷贝代码上（对应 Rust 的 `Clone: Send`）。
- 其余类型——IRef 接口装箱值、fun value、含非 Shareable 字段且无显式 ICopy 的裸
  IValueType——不可共享。持有它们的协程被固定（pin）。**固定不是错误，是保守回退**；
  编译器附带 `-Wconcurrency` 诊断给出固定原因链（"参数 1 `List<T>` 不可共享"、
  "触摸了全局 `x`"）。

两类特殊情况：

- `ValueShare` 是字段级递归判定，**不能直接复用现有的 `is_value_class`**：显式
  `impl IValueType` 的类不检查字段就能携带引用字段（见 2.3 节），槽位复制会共享这些
  引用，跨线程即数据竞争。Pass 10 必须自己遍历字段。
- 用户想让含引用字段的值类型跨线程，正确路径是显式 `impl ICopy<Self>` 并在 `copy()`
  里做出深拷贝——那时跨界的语义就是"调用用户代码得到副本"，与该类型处处一致的拷贝
  语义吻合。

### 4.3 全局变量

mut 且非 Sync 的全局变量实行**所有权封闭**：它属于初始化它的域（即 main），任何可能
触摸它的协程被固定到该域；Imm 全局（初始化后不变）可被任意线程读取；Sync 全局可被
任意线程使用。

最初提案中"编译后对所有全局变量分组、每组分配到不同线程"的静态方案不可行，原因有二：

1. **偷取是运行时事件**。哪些线程会运行哪些协程在编译期不可知，全局与线程的静态绑定
   无从建立。
2. **分组单位必须是对象图的连通分量，不是变量**。两个全局变量可以在运行时指向同一张
   对象图（别名），静态别名分析不可判定；按变量表分组会把一张图劈给两个线程。

"每组可去不同线程"的意图由后续的**组迁移**扩展实现（目标组静止时整体过户到另一线程
并附带其固定协程），第一版不做。

### 4.4 函数副作用

对每个函数（按可达调用闭包）保守累积：

```
Effects(f) = 可达的全部全局读写集合
           ∪ 可达的 extern 调用集合
           ∪ {unknown_virtual}   —— 接口虚调用取所有已知实现的并集；跨动态库边界
                                    （libmeta 未携带 effects）视为未知
           ∪ {meta_call}         —— #fun / 元编程调用（第一阶段一律视为未知）
```

extern 需要白名单（纯函数、C11 原子、线程安全 I/O）；不在白名单的 extern 使协程固定。

### 4.5 可偷判定

```
Stealable(async f(args)) ⇔
    每个参数类型 Shareable            （上下文类字段本身就是独立拷贝）
  ∧ 返回类型 R Shareable               （__SpawnFuture 需跨线程交付结果）
  ∧ Effects(f) 触摸的全局全部为 Imm 或 Sync
  ∧ 可达 extern 全部在白名单内
  ∧ 无 unknown_virtual，无 meta_call
```

返回类型出现在判定里是因为 spawn 的 join 协议本身跨线程：父线程轮询 future、子线程
写入 future（见 5.5）。

### 4.6 不变式与安全性论证

四条不变式构成正确性目标：

- **INV1（封闭）**：任何非 Sync 对象的可变访问只发生在其出生域的单个线程执行流中。
- **INV2（跨线程流）**：线程间传递引用只经 Sync 对象内部（其收发的值必须 Shareable）
  或 Imm 对象。
- **INV3（全局）**：mut 非 Sync 全局只在 owner 域被触摸；Imm 全局任意读；Sync 全局任意
  用。
- **INV4（GC）**：堆全局共享且非移动；标记只在停止世界的安全点进行。

对调度转移做归纳证明（骨架）：初始时单线程运行初始化例程，INV 平凡成立。归纳各情形：

1. **本地执行**——对象只在出生域被触摸：持有不可共享引用的协程由判定不可偷，永在出生
   线程；它创建的子协程默认同线程，传递闭包成立（INV1）。
2. **偷取**——只偷可偷协程；其携带状态全部 Shareable（INV2），可达全局全部 Imm/Sync
   （INV3）。
3. **跨线程消息**——通道是 Sync 且元素 Shareable（并行形态下编译期强制，INV2）。
4. **分配**——新对象属于当前线程的域。
5. **回收**——停止世界后枚举全部根（每线程主栈、全部协程栈扫描区、全局根、Sync 根），
   非移动堆保证跨线程指针永不失效（INV4）。

结论：无数据竞争（非 Sync 可变访问被单线程化）且无内存错误。不承诺的部分见 1.2 节。
调试模式提供纵深防线：对象头元数据（偏移 0）中放域标签，跨域引用流触发陷阱，用于在
静态分析可能的遗漏处及早失败。

## 5. 基础方案的六处修正

原提案的每处漏洞都有具体反例。修正后的模型即第 4 章的内容。

### 5.1 "创建时分析变量输入"不充分

栈式协程的执行可以**事后**获得引用。反例：

```
async worker() { let l = get_list(); l.push(1); }
```

零捕获，但 `get_list()` 返回全局列表的引用。可偷判定必须覆盖协程体的全部可达调用闭
包（4.4、4.5 节），创建点输入只是其中一项。

### 5.2 "只持有值类型"必须做字段级递归判定

反例：

```
class Holder { l: mut List<i64>; impl IValueType; }
```

`Holder` 被分类为值类型（显式标记不检查字段），其实例可内联在协程栈上并携带堆引用。
判定不能复用 `is_value_class`；这就是 `ValueShare` 独立递归的原因。值拷贝语义（2.3
节）保证了另一半前提：上下文类中的深值参数是独立副本，与发送方无别名。

### 5.3 string 的共享依据是不可变性

string 在分类层是"值类型"、在运行层是堆指针（2.3 节）。按字面规则它会被当作值随栈跨
线程，携带的堆指针随之跨界——这碰巧安全，但安全依据是 string 不可变（所有字符串操作
都产生新对象，无原地突变），必须以 `Imm` 显式入格，而不是混在"值类型"里。

### 5.4 全局变量分组改为所有权封闭

见 4.3 节。核心：静态的"组→线程"绑定不可行（偷取是运行时事件；运行时别名使分组单位
必须是对象图连通分量），第一版用所有权封闭 + Imm 只读共享 + Sync 共享。

### 5.5 spawn/join 协议自身产生跨线程引用

`async f(args)` 重写出的 `__SpawnFuture<R>` 被父线程轮询（`poll`）、被子线程写入
（`complete`），是一个货真价实的共享可变对象。可偷的 spawn 必须把 future 内部做成
Sync（原子完成标志 + Shareable 结果槽 + 父协程停靠队列）。由此自然导出一条原提案没有
的规则：**协程返回类型也必须 Shareable 才可偷**。上下文类 `__SpawnCtx` 本体在 spawn
语句块中只有 future 逃逸（重写形式已确认），可视为过户给子协程，无需额外处理。固定
的 spawn 父子同线程，future 保持现在的普通实现。

### 5.6 阻塞原语与 GC 停止点

两个运行时陷阱：

1. **阻塞原语必须下探为调度点**。如果 Mutex 用 OS 原语阻塞线程，会与固定协程组合出
   死锁：持锁协程可能排在同一线程的队列尾部永远轮不到运行。Sync 类型的阻塞操作必须
   停靠（park）当前协程、唤醒线程去执行其他任务，而不是阻塞线程本身。
2. **GC 需要安全点**（safepoint：保证执行到该点时可以安全暂停的世界静止位置）。纯计
   算、不分配、不停靠的协程会让停止世界停不下来；而它并发修改对象图会让标记漏边，回
   收仍被引用的对象。这不是延迟问题，是正确性问题。并行形态需要循环回边安全点轮询
   （每次迭代读一个全局世代号，约一条 load 指令；Go 语言的同款方案）。在 BSP 形态
   （第 6 章）下轮界屏障本身就是安全点，不需要循环轮询。

## 6. 与仿真语义的相容：BSP 并行轮

### 6.1 冲突

现行 delta-round 语义是确定性离散事件仿真：轮是全局屏障、虚拟时钟只在轮间推进、轮内
FIFO 顺序确定、静止指纹判定退出。自由的工作窃取会摧毁轮屏障与全序，两者不可直接调
和。出路不是放弃仿真语义，而是接受一个语言契约。

### 6.2 语言契约：轮内读写不可靠

**同一仿真时刻（delta 轮）内，跨协程读写理论上不可靠**；只有目标性停靠（event/
future/通道就绪）或仿真时间推进之后，读取才可靠。这是 SystemC 的立场（delta 内进程
求值顺序不规定），也是 Verilog 同一时间步竞争行为的立场。PenguinLang 的并发语义本就
源于 SystemC 一系，此契约不是新限制，而是把语系允许的事情写明。

### 6.3 sim-mt：整体同步并行（BSP）

在该契约下，仿真轮可以并行执行：

- 轮开始：快照就绪集，分发到 N 个线程（工作窃取，只偷可偷协程）；
- 轮内：各线程并行执行分到的协程；中途 spawn 按亲和性进当前线程队列（保持"spawn 当
  轮可跑"的现有性质）；
- 轮界：**全局屏障**——本轮全部协程跑完或停靠之后，单线程执行策略决策（队列轮转、
  定时器触发、时钟推进、fd 轮询、静止指纹）。

逐项核对现有机制：

| 机制 | sim-mt 下的处理 | 是否保持 |
|---|---|---|
| 轮内 FIFO 序 | 变为不规定（契约允许） | 语义合法；测试需审计（第 12 章） |
| 统一虚拟时钟 | `_sim_now_tick` 只在屏障段写，轮内只读（屏障提供可见性边） | 是 |
| 时钟推进决策 | 本来就是无进展轮的屏障决策 | 是 |
| 活动计数 `_sim_activity` | 原子递增 | 是 |
| 定时器注册 | 轮内进每线程暂存，屏障按（截止点，全局 spawn 序号）确定性归并 | 是 |
| fd 停靠与轮询 | 只在屏障段执行（单线程） | 是 |
| 静止指纹 | 屏障时刻全体停靠、栈冻结；按全局 spawn 序号归并的收养序迭代，仍确定 | 是 |
| 线语义同轮坍缩 | "最终值"的最终变为不规定（契约允许：同刻写入本不可靠） | 语义合法 |
| GC | **轮界屏障即天然停止世界**（见 8.1 节） | 是 |
| 不停靠不分配的死循环 | 与今天单线程行为一致（挂起，无回归） | 是 |

性能特征是 BSP 型的：每轮一次屏障（微秒级）。轮大（一轮多个进程，ESL 典型负载）收益
好；每轮一跳的反应式流水线受屏障开销限制——这是第 6.4 节第三形态的存在理由。

### 6.4 三形态

| | sim（默认，现状） | sim-mt（BSP） | free-mt（后期） |
|---|---|---|---|
| 线程 | 1 | N（轮内并行 + 轮界屏障） | N（自由工作窃取） |
| 时间 | 虚拟时钟、delta 轮 | 虚拟时钟、delta 轮（不变） | 墙钟；裸 `wait` 退化为让出 |
| 确定性 | 全确定 | 跨轮确定、轮内不规定 | 仅无数据竞争 |
| 通道/Event | 现实现 | 内部 Sync + 元素 Shareable | 同 sim-mt |
| GC 安全线 | 不需要 | 轮界屏障 | 循环回边轮询 |
| 用途 | ESL 建模、字节精确测试、LSP、自举 | 用户程序并行（保守） | 高吞吐服务（激进） |

同一份源码、同一套封闭分析与 ISync 库。编译器自身**永远以 sim 形态编译**（自举的
md5 收敛不受影响）。sim-mt 在 `--threads=1` 时必须与 sim 输出逐字节一致（差分测试的
锚点）。

## 7. 显式转移：Ownership\<T\>

### 7.1 原则：放置自动，转移显式

放置（placement，哪个协程去哪个线程）错误只损失并行度，保守自动推断是安全的。转移
（transfer，引用跨过线程边界）错误才是数据竞争，必须显式声明且可检查。据此确立总原则：

> **放置自动推断（保守安全）；转移显式声明（编译期检查）。**

跨线程传引用的唯一显式通道是所有权转移类型：

```
enum Ownership<T> { owned: T; not_owned; }

Ownership.owned(v)      // 构造：编译期验证独占性
o.move() -> T           // 消耗：置 not_owned；对 not_owned 再 move 为运行期错误
```

### 7.2 三条规则

1. **构造检查（编译期，函数内可判定）**。`Ownership.owned(v)` 只接受三类 `v`：
   - `new` 表达式（全新对象，别名不可能存在）；
   - 刚从另一个 Ownership 的 `.move()` 解出的值（独占性经上一环传递）；
   - **线性持有的局部**——从出生点到包装点：未逃逸进任何字段、全局、通道或普通调用
     实参；无别名绑定；未被取地址。违反即编译错误。
   跨阶段流水线转发链天然成立：上游收到的 `Ownership` 经 `.move()` 解包，结果再包装，
   起点仍是 move 结果。
2. **消耗检查（运行期）**。`.move()` 取出 payload 并把自身置 `not_owned`；对
   `not_owned` 再 `.move()` 触发运行期错误。语言没有线性类型，编译期无法跟踪消耗，
   显式操作上的运行期检查足够。
3. **跨线程许可**。通道与 spawn 把 `Ownership<T>` 视为合法的跨界元素，**无论 T 是什么
   引用类型**——独占性已由构造检查保证，接收方成为唯一持有者。

### 7.3 编译器特殊处理：payload 私有

`Ownership<T>` 是编译器内建特殊类型（与 `Box` 同级）。**payload 槽 `.owned` 的读和写
一律在绑定器拒绝**，错误信息指向 `.move()`。否则：

```
let a = foo.owned;    // 编译错误：直接漏出 payload，独占性作废
```

泄漏路径枚举与封堵：

| 路径 | 处理 |
|---|---|
| `.owned` 成员读 / 写 | 绑定器拒绝 |
| 元编程 / 反射合成的成员访问 | 走同一绑定器路径，同样拒绝 |
| `foo is Ownership<T>.owned` 标签测试 | 允许（纯标签判断，不解包 payload） |
| wrapper 本体的传递、存储、经通道发送 | 允许（wrapper 就是值的合法形态） |
| 本地 `let t = o.move();` 之后使用 `t` | 允许（普通局部值）；要跨线程必须重新 `Ownership.owned(t)` 包装，t 自 move 起重新纳入线性持有检查 |

### 7.4 与 GC 的对齐

移交点即提升点（第 8 章）。可偷协程收到 `Ownership` 后持有的是独占引用：没有其他线程
会碰它，即使该协程随后被再次偷取也不产生竞争；GC 侧其对象位于共享池（8.5 节），偷取
安全。所有权语义与 GC 完整性在同一点闭合。

## 8. GC 多线程化

### 8.1 v0：单堆 + 分配锁 + 屏障停止世界

第一版最保守：保持单一全局堆，分配加每大小类别锁；回收在轮界屏障（sim-mt）或安全点
（free-mt）停止世界后由单线程标记清扫。枚举全部根（每线程主栈水位协议照抄现有 main
协议；协程栈扫描区随句柄走）。非移动堆保证跨线程指针永不失效。此版本下 sim-mt 的轮界
分发可以任意进行（只有一个收集器、全根枚举），不存在下述 v1 的问题。

### 8.2 v1：分配类路由与远端局部危险

线程局部回收的前提是把堆拆开：每线程局部堆（线程局部 GC 回收，廉价、频繁）+ 共享堆
（全局停止世界 GC 回收，低频）。该设计通常最贵的部件是维护"**共享对象不得指向线程
局部对象**"这一指针方向不变式所需的写屏障。封闭模型在此提供了直接的契合：

> INV2 + ISync 元素强制 Shareable，意味着共享对象**结构上不可能**获得指向线程局部对象
> 的指针——Sync 容器的元素写入就是移交点，DeepVal 元素是纯值，Imm 元素本就共享。

于是线程局部 GC 把共享类对象当作不透明对象处理（不释放、不穿透追踪），只回收本线程
局部堆，无需任何写屏障。

但拆堆暴露一个必须封堵的漏洞——**远端局部**（remote-local）：如果偷取**已停靠的继续
体**（比如轮界把下一轮就绪队列任意分发），一个可偷协程的栈上持有它在本线程分配的局部
对象；恢复到线程 B 后，A 的局部 GC 已看不到它（根随句柄离开 A），B 的局部 GC 标记它
却不扫 A 的堆段——A 误回收，产生悬垂指针。

修复是**分配类路由**：每线程两套分配场所（局部 / 共享），分配时按当前执行上下文选择
——固定（pinned）执行 → 局部场所；可偷（stealable）执行 → 共享场所；静态类型为 Sync
的分配 → 恒定共享场所。这样可偷协程的所有分配天然在共享堆，停靠后任意偷取安全；固定
协程永不迁移，局部堆安全。开销接近零（场所指针本来就是每线程状态，模式位随执行上下
文走）。

### 8.3 Imm 惰性提升：一个例子

静态路由"Imm 类型 → 共享堆"有一个现实问题：string 是 Imm，而运行期字符串操作是最高
频分配。例子（线程 A 上的固定协程）：

```
fun summarize(samples: List<i64>) -> string {
    let sb: mut StringBuilder = new StringBuilder();    // 非 Sync 引用 → A 局部堆
    let i: mut i64 = 0;
    while (i < n) {
        let s: string = samples.at(i).some.to_string(); // Imm → 若静态路由则进共享堆
        sb.append(s);                                   // s 用完即死
        i = i + 1;
    }
    return sb.to_string();                              // 同上
}
```

若字符串静态路由进共享堆，短命字符串垃圾全部堆积在只有全局 GC 能回收的共享堆里，全局
停止世界 GC 的频率不降反升——对字符串密集负载（编译器自身、JSON、LSP）适得其反。

修复是**惰性提升**：Imm 对象默认进当前场所（固定执行 → 局部堆），只在真正跨线程的
**移交点**提升为共享类。移交点是一个封闭集合：Sync 通道写入、spawn 上下文填充、
Ownership 移交、全局初始化（初始化单线程，全局对象数量少，直接进共享场所）。上例中
`s` 若从不跨线程，就生死于 A 的局部堆，由局部 GC 廉价回收；只有真正 `ch.write(s)` 的
那一刻才付出提升成本（字符串扁平无孩子，提升为常数时间）。

### 8.4 为什么 Imm 免写屏障、可变图不行

提升要维持的方向不变式是"共享对象不指向局部对象"。可变对象被提升后，接收方仍可往里
**存入新的局部引用**，把不变式砸穿——这是经典的需要写屏障的场景。反例：线程 A 把
`Ownership.owned(list)` 发给 B，list 提升为共享类；B 的固定协程执行
`list.push(新字符串)`，新字符串分配在 B 局部堆——共享对象持有局部孩子；B 的局部 GC
不穿透共享类对象，看不到这个字符串，一旦 list 丢掉它，局部清扫误回收，产生悬垂。

Imm 对象没有这个问题：**不可变对象的子节点集合在构造时刻冻结**，永远不会通过存入操
作获得新孩子。因此"提升时传递遍历一遍全图（O(图大小)；已提升子树可经标志位跳过）"
之后，共享-Imm 永远不会再指向局部对象。零写屏障。

### 8.5 Ownership 跨域转移：按异域接收拷贝

可变图既不能提升后放任存入（8.4 的反例），也不该为此给每次堆字段存入加"目标是否共享
类"检查（并行构建下约 5–15% 的运行时税）。方案是**copy-on-foreign-receive**：

- 接收方取出 `Ownership` 时比对对象的归属域与当前线程；
- **同域：零拷贝**。封闭在同一域内的流水线（最常见的使用方式）保持今天的性能；
- **异域：深拷贝**。副本落在接收方场所（接收方若在可偷上下文则落共享场所），深拷贝
  带环检测（访问集合，O(图大小)）；拷贝时刻接收方是独占持有者，拷贝无竞争；原图留在
  发送方局部堆，发送方经构造检查不再持有引用，由其局部 GC 自然回收。

跨域转移 1MB 缓冲的代价约为一次内存复制（数十微秒），通常远小于其上的计算量。零拷贝
跨域 + 写屏障的替代方案留待实测数据再评估。

### 8.6 v1 完整不变式集

1. Sync 对象及其内部节点恒在共享场所；其一切变更发生在已持锁的 Sync 方法内（锁内提
   升/分配），语言层面不存在对它们的普通存入。
2. Imm 默认局部 + 移交点传递提升；子节点冻结 ⇒ 共享-Imm 永不指向局部。
3. Ownership 跨域走 copy-on-foreign-receive；同域零拷贝。
4. 可偷执行恒分配共享场所（其收到的 Ownership 拷贝也落共享场所）。

推论：语言层面**不存在**"共享类可变对象 + 普通存入"的组合，方向不变式全程成立，任何
路径都不需要写屏障。v0 单堆下以上全部机制不存在（Ownership 零拷贝直接安全），这决定
了 v0 → v1 的实施顺序。

## 9. 条件 ISync 与两级执行路径

### 9.1 机制

通道族按元素类型条件性地实现 `ISync`：`Fifo<T>` 当 T 可共享时注入带锁 + 停靠背压的
Sync 实现；当 T 不可共享（如携带引用的裸类型）时**不实现** `ISync`，保持今天的无锁
实现。判定与实现同源生成：Pass 10 的 `Shareable(T)` 是唯一事实源，`#specializing`
按谓词分叉注入两套实现——虚表随单态化实例变化正是 `#specializing` 的本职。

非 Sync 通道"强制两端同线程"不依赖任何新强制机制，它是封闭分析的自然推论：
`Fifo<RefT>` 非 Sync ⇒ 类型不可共享 ⇒ 不能经任何跨线程流传递 ⇒ 只能经 spawn 参数
（接收者固定到发送者线程）或本域全局分发 ⇒ 两端自动同域。

### 9.1.1 注意点

- **一致性（coherence）**：分析认为 `Fifo<T>` 是 Sync，当且仅当注入的实现真的有锁。
  谓词与实现必须同源生成。泛型接口（`ISink<T>`、`IChannel<T>`）的可共享性随参数走：
  标准库声明"Sync 当且仅当参数 Shareable"，由 Pass 10 消费。
- **静默固定需要可见性**：传引用的通道把整条流水线固定成单线程，程序正确但慢且无感
  知。`-Wconcurrency` 诊断提示（"元素类型不可共享，用户被固定到单域；跨线程转移请用
  Ownership"）。
- `__SpawnFuture<R>` 同理条件化：可偷 spawn 配 Sync future，固定 spawn 保持普通实现。

### 9.2 两级路径

全部机制合起来构成两级执行路径：

- **默认同域快路径**：无锁通道、零拷贝、线程局部堆——与今天的单线程行为同价。
- **显式跨域路径**：Shareable/Sync 通道，或 `Ownership` 所有权转移。

## 10. 已否决与挂起的方案

| 方案 | 处置 | 理由 |
|---|---|---|
| 动态冻结（freeze 位 + 写路径检查：观察到无可变引用即共享） | 挂起 | "观察到无可变引用"不可靠：可变性是逐绑定的权限不是对象状态；协程退出不清除其导出的引用；别名集合运行时不可枚举。执行冻结则需并行构建下每次堆字段存入加检查（约 5–15% 税），与 Ownership 覆盖重叠 |
| freshness 自动推断（通道写入点自动识别新鲜值） | 否决 | 被 `Ownership` 取代——违背"转移显式声明"原则；显式版还把检查从每个通道写入点收敛到构造点 |
| 零拷贝跨域 Ownership + 存入写屏障 | 挂起 | 写路径税；copy-on-foreign-receive 先行，待实测数据 |
| 只偷未运行的 spawn（继续体不换线程） | 否决 | 牺牲轮界分发自由度，并行度受损；分配类路由以近零成本解决同一问题 |
| BabyPenguin C# VM 实现多线程 | 否决 | 仅原生实现（与 io 标准库同例）；跨编译器语义一致性由 sim 形态保证 |
| 全局变量静态分组到线程 | 否决 | 见 4.3 节；由所有权封闭取代，组迁移为后续扩展 |

## 11. 运行时工程要点

- 原生原子量从零补充：C11 `__atomic` / Windows Interlocked 实现
  `AtomicI64/AtomicBool/AtomicU64`，接口对齐 BabyPenguin 现有内置。
- 同步原语：mutex（pthread / SRWLock）、停靠-唤醒（futex / WaitOnAddress）。Windows
  侧走 SRWLock + ConditionVariable，维持现有"不引入 winpthread"的链接约束。
- 阻塞型 Sync 操作一律停靠协程（5.6 节），互斥锁内含停靠队列。
- `print` 加锁保证行原子性；对象 id 计数原子化。
- C 微内核逐线程化：调度上下文、spawn 收件箱、主栈水位、运行队列（第一版互斥锁版，
  Chase-Lev 无锁双端队列后置）从单全局改为每线程。
- fd 轮询归属单一指定线程；句柄销毁只由归属域执行。
- 调试模式对象头域标签抽查作为静态分析的纵深防线（4.6 节）。
- 跨动态库（libmeta 未携带 effects）的 spawn 一律固定；libmeta v2 增加 effects 字段后
  放宽。
- 元编程（`#fun`）调用第一阶段一律使协程固定。

## 12. 测试与验证策略

- **AsyncTest 顺序依赖审计**（并行化前置）：逐例检查现有异步测试的期望输出是否依赖
  轮内 FIFO 序；依赖者改写为轮序稳定断言或显式时间推进后断言。
- 测试运行器增加顺序不敏感断言模式（行集合相等）；并行类别仅适用于原生编译器。
- 差分测试：同一程序 sim 与 sim-mt `--threads=1` 输出逐字节相等；`--threads=N>1` 行集
  合相等。
- ThreadSanitizer（clang `-fsanitize=thread`）调试构建进入 CI 周期任务；Windows 用
  WINE 冒烟。
- 随机任务图压测（spawn 深度、通道星型、全局触摸模式的组合）配合域标签断言。

## 13. 结论与开放问题

设计收敛为一个封闭的模型：类型层面的共享格（Sync / Imm / ValueShare / Ownership /
显式 ICopy）驱动编译期封闭分析与条件 ISync，运行时以 BSP 并行轮使用多核，GC 以分配类
路由拆两级并全程免写屏障。所有安全性论证最终都落在两个前提上——**不可变性**（Imm：
共享安全 + 子节点冻结）与**独占性**（Ownership：转移安全 + 提升无竞争）——两者互相独
立又互相补位。

开放问题：

1. 动态冻结的重启条件：若实测写路径税低于估计，或 Ownership 深拷贝成为瓶颈。
2. 组迁移（全局对象图整体过户 + 附带固定协程搬迁）的设计。
3. libmeta v2 的 effects 字段与跨库可偷判定。
4. free-mt 形态的完整设计：去屏障后的静止判定、退出协议、唤醒协议。
5. Ownership 深拷贝的环检测在大图上的性能；字符串惰性提升的实测收益。
6. 循环回边安全点轮询的代码生成细节（仅 free-mt 需要）。
